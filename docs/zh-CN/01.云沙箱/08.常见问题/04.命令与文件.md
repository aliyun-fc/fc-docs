# 命令与文件

## 命令没有输出，怎么办？

先同时看 stdout、stderr 和退出码。很多工具会把错误写入 stderr，把日志写入文件，或在后台进程中继续运行。

```typescript
const result = await sandbox.commands.run("python3 script.py");
console.log(result.exitCode);
console.log(result.stdout);
console.error(result.stderr);
```

## 命令返回非 0 退出码，是否一定是云沙箱问题？

不一定。非 0 退出码通常说明命令本身失败，常见原因是依赖缺失、路径错误、权限不足、网络失败或参数错误。

先用同一模板执行最小命令，再逐步增加业务依赖。不要直接把所有失败归因于 Sandbox 创建问题。

## 什么时候需要 PTY？

只有命令依赖终端行为时才使用 PTY，例如交互式 CLI、读取 TTY、彩色输出、进度条或需要持续输入的命令。

普通批处理、测试、构建和脚本执行不建议默认开启 PTY，否则 stdout/stderr 解析会更不稳定。

## 后台命令启动后，为什么访问不到服务？

常见原因是服务没有监听目标端口、启动后立即退出、监听在错误地址，或依赖还没初始化完成。

先在 Sandbox 内检查端口和日志，再调用 `sandbox.getHost(port)`。不要只根据后台命令返回成功判断服务已就绪。

## 文件写入后命令读不到，怎么排查？

检查路径、时序、工作目录和权限。生产任务建议使用绝对路径，并为每个任务创建独立目录，例如 `/tmp/tasks/<task-id>`。

如果多次执行涉及不同 Sandbox 或不同执行上下文，也要确认文件写入和命令执行发生在同一个环境里。

## 上传下载 URL 可以长期保存吗？

不建议将 URL 作为长期文件地址。它指向当前 Sandbox 中的指定路径，应限制 Sandbox 生命周期、文件路径和数据敏感性，也不要把包含敏感数据的 URL 写入日志或暴露给无关用户。

需要让未持有 SDK 鉴权信息的浏览器或下游系统直接访问 URL 时，创建 Sandbox 时需设置 `secure=false`；否则请求方必须携带 `X-Access-Token`。`secure=false` 会降低访问保护强度。需要长期保存或分发的文件，应写入 OSS、NAS、数据库或业务存储。

## `run_code` 失败，先查什么？

先确认使用的是 `e2b-code-interpreter` 或 `@e2b/code-interpreter` SDK，以及 Code Interpreter 模板，例如 `code-interpreter-v1`。通用 `e2b` SDK 不提供 `run_code` / `runCode`。

再检查 Python、工作目录和必要依赖是否存在。

```bash
python3 --version
which python3
pwd
```

如果普通命令能执行但 `run_code` 失败，重点排查模板是否包含代码解释器所需服务和启动逻辑。

## 多次执行之间变量会保留吗？

只有 Code Interpreter 在同一个 Code Context 中执行时，变量、导入和解释器状态才会保留。`sandbox.commands.run()` 每次启动独立进程，不能依赖 Shell 变量跨调用保留。

换 Sandbox、换 Code Context 或终止后重建，都不应假设变量还在。

业务结果应写入文件或外部存储，不要只保存在解释器内存变量里。

## 直接调用 FC 或通过 Gateway 挂载存储失败，如何排查？

先辨认本次操作是首次创建、Session 附加、追加，还是已有挂载上的数据 I/O；并区分直接调用 FC 与经 Gateway 调用。不要根据控制面请求成功、`204`、目录存在或单项 `mountinfo` 判断数据已可读写，也不要盲目重试。Append 失败前后需保护已有挂载：核对 Sandbox 与挂载状态，并用已知对象验证旧路径。

如果实际响应的 `Message` 含以下精确方括号诊断码，按对应方向自助排查。诊断码是基于有限信号的 best-effort 提示，可能误判或遗漏，不是根因证明；不会替代原 HTTP 状态、FC `Code` 或重试行为。`243`、`521` 是客户端退出信息，不等同于 HTTP 或 FC 错误码，也不保证直接出现在 API 响应中。没有诊断码或遇到未知码时，使用 `STORAGE_MOUNT_FAILED` 的通用清单。`403`、`AccessDenied` 或 `EACCES` 可能来自权限、凭据、Bucket Policy、前缀或操作差异，不能单独断定 RAM 根因。

### `[OSS_PERMISSION_ERROR]`

- **含义：** OSS 访问可能受限；不表示已确认 RAM 策略拒绝。
- **可能原因：** 执行 Role 缺少所需操作权限、Role 信任关系未允许 FC 获取凭据、Bucket Policy 或条件存在显式拒绝、对象前缀不匹配，或临时凭据无效。
- **按检查成本从低到高排查：**
  1. 确认失败的是读取已知对象、写入对象还是列目录，并核对 Bucket、`bucketPath` 和 `readOnly`。`GetObject`（读对象）、`PutObject`（写对象）和 `ListObjects`（列举）是不同操作；列举失败只代表列举失败，不等于对象读写失败。
  2. 确认创建 Sandbox 时配置的 `fc.sandbox.auth.role` 是预期 Role；请管理员检查其信任关系是否允许 FC 获取凭据。信任关系允许获取凭据不代表 Role 已获 OSS 操作权限。
  3. 请管理员检查 Role 和目标 Bucket 的策略是否允许精确的操作、Bucket、对象前缀及 `oss:Prefix` 条件。Bucket Policy 或其条件中的显式 `Deny` 可覆盖其他策略的允许结果。
  4. 只有确认缺少授权时才补最小权限：读取只授予目标对象前缀所需的 `oss:GetObject`；可写挂载才授予所需的 `oss:PutObject`；客户端初始化或工作流需要列举时，才授予受 `oss:Prefix` 限制的 `oss:ListObjects`。部分客户端即使不执行 guest 列目录也会在初始化时列举。不要授予通配 `oss:*`，不要扩大到无关 Bucket 或前缀。
- **修复后验证：** 分别验证所需对象读取和目录列举。仅对可写挂载，在安全位置写入唯一测试对象并完成 flush、fsync、close、重新打开和读回；只读挂载不要写。

### `[OSS_CREDENTIAL_ERROR]`

- **含义：** OSS 临时凭据可能无效或过期；不等于已确认凭据是根因。
- **可能原因：** 创建 Sandbox 时执行 Role 配置错误、Role 信任关系变化，或凭据提供链未能取得或刷新有效 STS 临时凭据。
- **按检查成本从低到高排查：**
  1. 确认创建 Sandbox 时配置的执行 Role 是预期 Role；追加请求不会替换 Role 或扩大权限。
  2. 请 Role 管理员检查信任关系，再通过受支持的凭据提供方查看临时凭据过期和刷新状态。只查看状态，不复制、打印或发送 AK、Token 或 STS 凭据。
  3. 按该凭据链支持的方式刷新临时凭据。若当前 Sandbox 无法取得新凭据，按产品支持的 Sandbox 生命周期重新配置或创建；不要手工把 Token 填入请求，也不要盲目重复追加。
  4. 若凭据状态正常但仍失败，继续按 `OSS_PERMISSION_ERROR` 检查目标权限和 Bucket Policy；工具的 `Invalid Credentials` 也可能伴随实际访问拒绝。
- **修复后验证：** 凭据提供方确认刷新后，用已知对象验证实际读取；可写挂载再安全验证唯一测试对象的写入和读回。控制面请求成功不证明凭据有效或数据面 I/O 成功。

### `[OSS_TARGET_ERROR]`

- **含义：** OSS Bucket 或 Endpoint 可能配置错误。
- **可能原因：** Bucket 名称或地域不正确、Endpoint 与 Bucket 实际地域不匹配，或 Bucket 不存在。
- **按检查成本从低到高排查：**
  1. 对照预期目标核对配置中的 Bucket 名称与 `bucketPath`，包括对象前缀。
  2. 确认 Bucket 实际地域，并检查配置的 OSS Endpoint 是否属于该地域；不要只根据错误文本猜测地域。
  3. 通过有权限的存储管理入口确认目标 Bucket 存在且目标正确；无法确认时请 Bucket 管理员核对，不要改指向其他 Bucket。
- **修复后验证：** 修正已确认的名称、地域或 Endpoint 后，从挂载中读取已知对象；可写挂载才另外验证唯一测试对象的写入和读回。

### `[STORAGE_NETWORK_ERROR]`

- **含义：** 挂载阶段可能无法访问存储 Endpoint。
- **可能原因：** Endpoint 无法解析、DNS 配置异常、网络路由或出站访问受限，或连接超时；超时本身不证明根因一定是网络。
- **按检查成本从低到高排查：**
  1. 核对 Bucket 地域和 Endpoint 拼写。
  2. 从 Sandbox 所在网络检查该 Endpoint 的 DNS 解析和连接可达性，再检查适用的 VPC、路由和出站规则。
  3. 若 DNS 或网络不可达，请网络管理员修复对应解析、路由或出站规则；不要用扩大 OSS 权限来处理网络错误。
- **修复后验证：** 确认 Endpoint 可解析、可连接后读取已知对象，验证实际 I/O；可写挂载才验证唯一测试对象的写入和读回。

### `[STORAGE_MOUNT_FAILED]`

- **含义：** 已确认挂载失败，但没有足够信号继续细分；这是带排查清单的通用回退。
- **可能原因：** 存储配置、执行 Role、目标 Bucket/Endpoint、凭据、网络或其他挂载阶段条件。
- **按检查成本从低到高排查：**
  1. 确认 Sandbox 状态、存储类型、挂载路径和本次操作；追加失败不代表新挂载已回滚，也不代表旧挂载失效。
  2. 对照对应存储类型的产品说明检查 Bucket/前缀、地域/Endpoint、`readOnly` 和创建 Sandbox 时配置的执行 Role。
  3. 分别检查列目录、读取已知对象和写入新对象。无 List 时列举失败不证明对象读写失败，也不保证所有存储、runtime 和版本都支持可用的无 List 流程。
  4. 只修正已确认的问题；发起新的追加请求前先核对 Sandbox 和现有挂载状态，不要盲目重试。
- **修复后验证：** 按挂载权限读取已知对象；仅对可写挂载使用安全位置中的唯一测试对象，并完成 flush、fsync、close、重新打开和读回。不要覆盖业务数据。

做完以上检查后仍无法解决，再联系产品支持。直接调用 FC 时提供同次实际响应的 HTTP 状态、FC `Code`、`Message` 和 `RequestId`；经 Gateway 调用时提供 Gateway 响应中的 `RequestId`，如需关联 FC `RequestId`，按产品支持流程提交同次请求信息。可补充操作、入口、地域和时间。不要分享 AK、STS 凭据、Token、SDK Data 或原始日志。

> 追加挂载后的 `204` 只表示请求已接受，不代表存储 I/O 成功。具体验证顺序见[追加挂载沙箱存储](../04.功能说明/07.FC 扩展/09.追加挂载沙箱存储.md)。

## 缺少 OSS List 权限是否一定不能挂载？

不能仅凭缺少 OSS List 权限或目录列举失败判断挂载一定失败，也不能据此保证挂载一定可用。列举与对已知对象执行读取或写入是不同操作；应分别记录列举结果，并读取一个已知对象来验证实际 I/O。仅对可写挂载，才使用安全位置中的唯一测试对象并完成 flush、fsync、close、重新打开和读回；只读挂载不执行写入。具体无 List 行为可能随存储、runtime 和发布版本变化，不要推广为所有版本均支持无 List 挂载。
