# 用户委托 OAuth 注入

用户委托 OAuth 用于代表某个登录用户访问其个人资源，例如查询用户的钉钉信息、读写其飞书文档、访问其 Microsoft 365 文件（对应 Agent Identity 的 `USER_FEDERATION` 流程）。与 M2M OAuth 使用应用自身身份不同，它需要用户先完成授权。建议先阅读[凭证注入概述](./01.凭证注入总览.md)了解整体框架。

## 适用场景

M2M OAuth 使用应用自身的身份，而部分场景需要代表某个登录用户访问其个人数据：查询其钉钉信息、读写其飞书文档、访问其 Microsoft 365 文件。这类场景使用用户委托 OAuth。

与 M2M 最大的不同在于需要用户先授权。因此除了注入 Token，还多了一步引导用户授权的流程。

## 两种绑定用户的方式

创建沙箱时，需要告诉平台这个沙箱代表哪个用户，二选一：

| 方式 | 适用 | 需提供 |
| --- | --- | --- |
| JWT | 您的登录系统能签发 Agent Identity 信任的用户 JWT | 当前登录用户的有效 JWT（原始串，不加 `Bearer`） |
| UserId | 您用自建登录系统，用业务用户 ID 标识用户 | 一个稳定、唯一的用户 ID，如 `tenant-a:user-123` |

JWT 由 Agent Identity 验证；UserId 则由您的后端确认登录用户后提交，平台信任您给的值。同一用户始终用同一个值，不同用户不能复用。

## 使用前提

在 Agent Identity 里先准备好：

1. 创建 Workload Identity，并关联一个可用的 RAM Role；
2. 使用 JWT 方式时，创建身份提供商，并将该身份提供商关联到 Workload Identity；
3. 给关联的 RAM Role 授予 `agentidentitydata:GetResourceOAuth2Token` 权限；
4. 创建 OAuth 凭证提供商，配好授权端点、Token Endpoint、Client ID、Client Secret 和重定向地址；
5. 允许该 Workload Identity 使用这个 OAuth 凭证提供商；
6. 您的后端准备好有权创建或访问沙箱的平台调用凭证；
7. 确认目标服务的域名、认证 Header、scopes 等。

这些创建或更新沙箱的调用都在您的后端执行，用平台调用凭证鉴权，不能仅凭用户 JWT 操作沙箱。

## 配置沙箱

假设当前登录用户是张三，身份是 `my-agent`，Provider 是 `dingtalk-provider`，目标是 `api.dingtalk.com`。您的后端先从登录会话取得张三的 JWT（下面的 `currentUserIdToken` 或 `current_user_id_token`），然后创建沙箱：

**Node.js**

```typescript
import { Sandbox } from "e2b";

const sandbox = await Sandbox.create("code-interpreter-v1", {
  metadata: { "fc.sandbox.identity.name": "my-agent" },
  network: {
    allowOut: ["api.dingtalk.com"],
    denyOut: ["0.0.0.0/0"],
    rules: {
      "@fc.sandbox.identity": [{
        transform: { headers: {
          "fc.sandbox.identity.oauth.userFederation.jwt": currentUserIdToken,
        } },
      }],
      "api.dingtalk.com": [{
        transform: { headers: {
          "x-acs-dingtalk-access-token":
            "${fc.sandbox.identity.oauth.userFederation:dingtalk-provider}",
        } },
      }],
    },
  },
});
```

**Python**

```python
from e2b import Sandbox

sandbox = Sandbox.create(
    template="code-interpreter-v1",
    metadata={"fc.sandbox.identity.name": "my-agent"},
    network={
        "allow_out": ["api.dingtalk.com"],
        "deny_out": ["0.0.0.0/0"],
        "rules": {
            "@fc.sandbox.identity": [{
                "transform": {"headers": {
                    "fc.sandbox.identity.oauth.userFederation.jwt":
                        current_user_id_token
                }}
            }],
            "api.dingtalk.com": [{
                "transform": {"headers": {
                    "x-acs-dingtalk-access-token":
                        "${fc.sandbox.identity.oauth.userFederation:dingtalk-provider}"
                }}
            }]
        },
    },
)
```

要点如下：

- 用户身份放在保留控制项 `@fc.sandbox.identity` 里（它不是真实域名，不注入业务请求，也不要放进 `allowOut`）。
- 引用表达式是 `${fc.sandbox.identity.oauth.userFederation:<提供商名>}`。
- 用 UserId 方式时，把 `...userFederation.jwt` 那行换成 `"fc.sandbox.identity.oauth.userFederation.userId": currentUserId` 即可，其余不变。JWT 和 UserId 二选一，同时提供会失败。

如果张三已经授权过，创建直接成功；如果尚未授权，创建会返回待授权错误（见下一节）。

## 验证凭证注入

创建成功后，在沙箱内直接请求目标服务，无需携带认证 Header：

```bash
curl -i https://api.dingtalk.com/v1.0/contact/users/me
```

请求出站时，网关会注入张三的钉钉 Token。

## 用户尚未授权时的处理

这是用户委托 OAuth 特有的一步。当张三尚未授权时，创建或更新会返回 HTTP 403，错误码 `ResourceAuthorizationRequired`，并在 `details.authorizations` 里一次给出所有需要授权的 Provider 和授权 URL：

```json
{
  "code": "ResourceAuthorizationRequired",
  "message": "User authorization is required.",
  "details": {
    "authorizations": [
      { "providerName": "dingtalk-provider",
        "authorizationUrl": "https://auth.example.com/authorize/dingtalk" }
    ]
  }
}
```

处理流程：

1. 您的程序识别这个错误，把 `authorizationUrl` 展示给张三（用响应里的真实 URL，不要自行拼接）；
2. 张三打开 URL，完成第三方登录和授权；
3. 全部授权完成后，您的程序重新提交原来的创建请求；
4. 这次平台能取得 Token，沙箱创建成功。

返回待授权错误时未创建沙箱（若是更新，则整次不生效）。完成部分授权不会让配置部分生效，需全部授权后再重试。

## 会话绑定（state 与 callbackUrl）

如果您在 Workload Identity 里开启了会话绑定，创建时要多带两个字段，用来在授权回调时校验是不是同一个用户发起的：

**Node.js**

```typescript
import { randomBytes } from "node:crypto";
import { Sandbox } from "e2b";

const authorizationState = randomBytes(32).toString("hex");
const callbackUrl = "https://customer.example.com/oauth/callback";

const sandbox = await Sandbox.create("code-interpreter-v1", {
  metadata: { "fc.sandbox.identity.name": "my-agent" },
  network: {
    allowOut: ["api.dingtalk.com"],
    denyOut: ["0.0.0.0/0"],
    rules: {
      "@fc.sandbox.identity": [{
        transform: { headers: {
          "fc.sandbox.identity.oauth.userFederation.jwt": currentUserIdToken,
          "fc.sandbox.identity.oauth.userFederation.state": authorizationState,
          "fc.sandbox.identity.oauth.userFederation.callbackUrl": callbackUrl,
        } },
      }],
      "api.dingtalk.com": [{ transform: { headers: {
        "x-acs-dingtalk-access-token":
          "${fc.sandbox.identity.oauth.userFederation:dingtalk-provider}",
      } } }],
    },
  },
});
```

**Python**

```python
import secrets

from e2b import Sandbox

authorization_state = secrets.token_hex(32)
callback_url = "https://customer.example.com/oauth/callback"

sandbox = Sandbox.create(
    template="code-interpreter-v1",
    metadata={"fc.sandbox.identity.name": "my-agent"},
    network={
        "allow_out": ["api.dingtalk.com"],
        "deny_out": ["0.0.0.0/0"],
        "rules": {
            "@fc.sandbox.identity": [{
                "transform": {"headers": {
                    "fc.sandbox.identity.oauth.userFederation.jwt":
                        current_user_id_token,
                    "fc.sandbox.identity.oauth.userFederation.state":
                        authorization_state,
                    "fc.sandbox.identity.oauth.userFederation.callbackUrl":
                        callback_url
                }}
            }],
            "api.dingtalk.com": [{"transform": {"headers": {
                "x-acs-dingtalk-access-token":
                    "${fc.sandbox.identity.oauth.userFederation:dingtalk-provider}"
            }}}]
        },
    },
)
```

发起创建前，请把 `authorizationState` 或 `authorization_state` 与当前登录会话的关联存入您自己的存储，供回调校验。

开启会话绑定后的授权流程多一步：授权回调到您的 `callbackUrl` 时，您的后端要校验 `state` 和当前登录用户，再用回调带来的 `session_uri` 调用 `CompleteResourceTokenAuth`，然后才重试原请求。`state` 由您生成和校验，平台只原样透传。

未开启会话绑定时无需处理 `state` 与 `callbackUrl`，用户按 Agent Identity 的流程授权完成后，直接重试原请求即可。

## 更新配置与切换用户

沙箱运行期间可更新注入规则或切换用户，具体操作见[更新网络配置](../04.更新网络配置.md)。切换用户时，在保留控制项中提交新的 JWT 或 UserId。

用户身份更新规则：

- JWT 与 UserId 二选一，都省略则保留当前用户身份。
- 每次提交 JWT 都会重新验证。切换用户不要求和原来是同一个人。
- 只支持运行中的沙箱；暂停的要先恢复。

JWT 与 UserId 的更新规则只适用于用户委托 OAuth。
