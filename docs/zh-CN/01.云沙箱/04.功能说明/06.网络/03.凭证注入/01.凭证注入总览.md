# 凭证注入概述

沙箱内的代码常需要访问外部服务，例如阿里云 OSS、第三方模型 API、钉钉、飞书等，这些请求都需要携带凭证（AK、API Key、OAuth Token）。凭证注入让真实凭证无需进入沙箱：凭证保存在沙箱外（您的控制端或阿里云 **Agent Identity**），沙箱内代码使用占位凭证正常发起请求，请求离开沙箱时由**出网网关**替换为真实凭证再转发。真实凭证不进入沙箱的进程、环境变量或文件。

多数方式底层都是同一个机制：`network.rules` 在出网请求上改写 Header、注入凭证，差异只在于凭证来源。访问阿里云服务是一个例外，它不注入 Header，而是由网关用真实 STS 重新签名，见下文。

- **自带凭证**：您把真实凭证（或占位符与真实值的映射）写入配置，平台负责注入。参见[自带凭证注入](./02.自带凭证注入.md)。
- **由 Agent Identity 托管凭证**：您只需写一个**引用表达式**，平台负责从 Agent Identity 获取、刷新真实凭证并按用户隔离。见下文托管方式。

大多数场景用自带凭证即可。

## 配置沙箱

如果您已经持有真实凭证（如一个 API Token），创建沙箱时在 `network.rules` 里声明把它注入到某域名的某个 Header，沙箱内代码正常发起请求即可，出网时由网关注入真实凭证。

**Node.js**

```typescript
import { Sandbox } from "e2b";

const token = process.env.API_TOKEN;

const sandbox = await Sandbox.create({
  network: {
    allowOut: ["api.example.com"],
    denyOut: ["0.0.0.0/0"],
    rules: {
      "api.example.com": [{
        transform: {
          headers: { Authorization: `Bearer ${token}` },
        },
      }],
    },
  },
});
```

**Python**

```python
import os

from e2b import Sandbox

sandbox = Sandbox.create(
    network={
        "allow_out": ["api.example.com"],
        "deny_out": ["0.0.0.0/0"],
        "rules": {
            "api.example.com": [{
                "transform": {
                    "headers": {
                        "Authorization": f"Bearer {os.environ['API_TOKEN']}"
                    }
                }
            }]
        },
    },
)
```

占位符替换等用法参见[自带凭证注入](./02.自带凭证注入.md)，通用限制参见[凭证使用限制](./07.凭证使用限制.md)。

如果需要平台自动刷新凭证、按用户隔离，或访问阿里云服务，再参考下面的托管方式。

## 托管方式：Header 注入

以下三种方式与自带凭证的注入机制完全一致，都通过 `network.rules` 的 `transform.headers` 注入，区别仅在于把真实值换成指向 Agent Identity 的引用表达式。按目标服务类型选择：

| 目标服务 | 引用表达式对应的方式 | 文档 |
| --- | --- | --- |
| 使用 API Key 的服务（模型服务、搜索、内部 API） | API Key 注入 | [托管凭证注入](./04.托管凭证注入.md) |
| 使用应用身份访问的 OAuth 服务（钉钉企业应用、Microsoft Graph、Auth0） | M2M OAuth | [M2M OAuth 注入](./05.M2M%20OAuth%20注入.md) |
| 代表登录用户访问其个人资源（用户的钉钉、飞书、M365 文件） | 用户委托 OAuth | [用户委托 OAuth 注入](./06.用户委托%20OAuth%20注入.md) |

三种方式的含义：

- **API Key 注入**：引用一个存储在 Agent Identity 的 API Key，平台取出后注入 Header。
- **M2M OAuth**：平台用应用自身身份换取并刷新 OAuth Token。
- **用户委托 OAuth**：平台用某个登录用户的身份换取 Token，按用户隔离，需用户先完成授权。

以 API Key 为例，托管与自带凭证注入到目标服务的效果相同，差别仅在于 Key 存在您这边还是 Agent Identity。托管的额外能力在于生命周期：M2M OAuth 与用户委托 OAuth 的 Token 有有效期，平台会自动刷新；用户委托 OAuth 还按登录用户隔离。

## 托管方式：访问阿里云服务（重签）

访问 OSS、ECS、VPC、FC 等阿里云服务与上面三种不同。它不注入 Header，而是让网关用真实 STS 对整个请求**重新签名**：沙箱内用占位 AK 正常调用阿里云 SDK，出网时由网关重签，真实 AK 始终不进沙箱。配置也不走 `network.rules`，而是在创建沙箱时通过 `metadata` 的身份字段声明。详见[阿里云 STS 注入](./03.阿里云%20STS%20注入.md)。

## 工作流程

无论哪种方式，流程都是以下三步：

```text
1. 准备凭证：自带，或托管在 Agent Identity
        ↓
2. 创建沙箱时，声明该沙箱向哪个域名的哪个 Header 注入什么凭证
        ↓
3. 沙箱内代码正常发起请求 → 出网网关替换为真实凭证 → 目标服务收到正常请求
```

配置结构在自带凭证与三种 Header 注入方式间共用：`network.rules` 里为每个域名配置一条 `transform.headers` 规则，自带凭证填真实值，托管方式填引用表达式。访问阿里云服务不走 `network.rules`，改用 `metadata` 的身份字段声明。

## 通用约定

无论哪种方式，以下两点都成立。

**放行网络与注入凭证是两件独立的配置。** 让沙箱能访问某域名，依赖 `network.allowOut`（网络策略）；让该域名的请求携带真实凭证，依赖 `metadata` 里的身份配置或 `network.rules`。只配置注入而未放行网络，请求仍会被网络策略拦截；配置域名注入也不会自动放开网络。

**真实凭证不进入沙箱。** 真实凭证保存在沙箱外，出网时才由网关注入，沙箱内无法读取；沙箱内可用占位凭证代替，使 SDK 正常生成请求。托管方式下，平台负责获取、缓存、刷新真实凭证，查询沙箱信息只能看到引用表达式（如 `${fc.sandbox.identity.apiKey:xxx}`）；自带凭证方式查询会明文回显所填的值，因此不要把查询响应写入日志。
