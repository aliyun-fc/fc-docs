# 用户与工作目录

模板中的用户和工作目录会影响命令执行、文件权限和依赖安装位置。Agent 场景中，建议保持工作目录稳定，避免每次执行命令都依赖隐式路径。

## 查看当前用户和目录

```typescript
const result = await sandbox.commands.run("whoami && pwd");
console.log(result.stdout);
```

Python 示例：

```python
result = sandbox.commands.run("whoami && pwd")
print(result.stdout)
```

## 指定命令工作目录

```typescript
await sandbox.files.makeDir("/tmp/project");
await sandbox.files.write("/tmp/project/main.py", "print('hello')\n");

const result = await sandbox.commands.run("python3 main.py", {
  cwd: "/tmp/project",
});

console.log(result.stdout.trim());
```

Python 示例：

```python
sandbox.files.make_dir("/tmp/project")
sandbox.files.write("/tmp/project/main.py", "print('hello')\n")

result = sandbox.commands.run(
    "python3 main.py",
    cwd="/tmp/project",
)

print(result.stdout.strip())
```

## 默认用户与 UID（第二代运行时）

模板的默认用户是 `user`，默认工作目录是 `/home/user`（也可以在模板的 `steps` 里指定，见下节「自定义默认用户与工作目录」）。平台保证该账号在沙箱内存在且可用：

- UID/GID 优先取 1000。如果镜像中 1000 已被其他账号占用（例如 `ubuntu:24.04` 的 `ubuntu`、`node` 镜像的 `node`），平台会顺延使用 1001、1002 等下一个可用 UID，不会因此拒绝启动。
- 镜像中已有 `user` 账号时，平台直接使用该账号及其 UID。
- 平台会为默认主目录（默认 `/home/user`）准备属主：目录不存在则创建，存在则把该目录及其内容的属主调整为默认用户，保证默认可写。这个处理只作用于默认主目录，镜像中其他路径的属主不变——由镜像自带账号或 root 拥有的 `/srv/app` 这类目录，`user` 仍可能写不进去，需要在 Dockerfile 里提前调整属主，或在命令里用 `sudo`。
- `commands.run`、启动命令和就绪命令默认都以 `user` 执行，`commands.run` 的 `cwd` 可按次覆盖。实际身份可以在沙箱内用 `sandbox.commands.run("id")` 查看。
- 如果 UID 1000 被镜像中的业务账号占用并拥有应用文件，而应用以 `user` 运行，`user` 可能没有这些文件的写权限。需要在 Dockerfile 中提前调整属主。
- 不要把 UID 1000 写死在 `chown`、sudoers、配置文件或路径中。判断身份时使用用户名 `user`，需要可写目录时使用 `$HOME` 或 `/home/user`。

## 自定义默认用户与工作目录

第二代模板可以通过 POP OpenAPI `CreateTemplate` 的 `runtimeConfig.sandboxConfig.steps` 声明 `USER` 和 `WORKDIR`。构建期按声明创建账号和目录，沙箱的默认身份与默认工作目录取最后一条 `USER` / `WORKDIR`：

```json
{
  "name": "my-template",
  "teamId": "<your-team-id>",
  "runtimeConfig": {
    "cpu": 2,
    "memorySize": 2048,
    "diskSize": 15360,
    "sandboxConfig": {
      "generation": 2,
      "image": "registry-vpc.cn-shanghai.aliyuncs.com/example/app:v1",
      "steps": [
        {"type": "USER", "args": ["app"]},
        {"type": "WORKDIR", "args": ["/home/app"]}
      ]
    }
  }
}
```

- `USER` 的 `args[0]` 是账号名；账号不存在时在构建期创建，之后 `commands.run`、启动命令和就绪命令都以该账号执行。
- `WORKDIR` 的 `args[0]` 是工作目录；只声明 `USER` 不会自动切换工作目录，需要非默认目录时请同时声明 `WORKDIR`。
- 未声明 `USER`/`WORKDIR` 时回落 `user` / `/home/user`。
- 镜像的 OCI `USER`（Dockerfile 里 `USER` 的产物）不参与默认身份判定，**不生效**；从 Dockerfile 迁移镜像时请显式写 `USER` step。
- 该能力目前只在 POP OpenAPI 的 `CreateTemplate` 上开通。通过 E2B Template 定义内联传 `steps` 仍会返回 `400 steps are not supported`，E2B SDK 的 `set_user`/`set_workdir` 需要改写为 POP steps。
- 仅第二代运行时支持构建期 `steps`；第一代传入 `steps` 会返回 400。`COPY` 暂不支持。

## 使用建议

- 模板构建时固定常用工具和依赖。
- 任务运行时使用明确的 `cwd`。
- 不要假设所有镜像都有相同默认用户、HOME 目录和权限。
- 不要假设默认用户的 UID 一定是 1000；需要固定 UID 时在镜像中自带 `user` 账号。
