# Mount an AgenticBucket Volume

When creating a sandbox, use `volume_mounts` to mount an existing AgenticBucket Volume to a specified directory. The sandbox can then access the BucketSpace through file paths, and the data is not deleted when the sandbox is released.

The AgenticBucket must already exist. The BucketSpace does not need to exist before the mount. If it does not exist, the system creates it during the first mount.

## Prerequisites

- An AgenticBucket Volume has been created for the target Team, and its Volume name is available.
- An FC Agent Sandbox API key bound to the same Team is ready. A Volume and API key cannot be used across Teams.
- A function execution RAM Role is ready. The Role has read and write permissions on the target AgenticBucket and BucketSpace, and its trust policy allows the Function Compute service to assume it.
- The FC Agent Sandbox API URL, domain, and an available template are ready.

You do not need to disable `BlockPublicAccess` for the AgenticBucket. The sandbox uses the execution Role to obtain temporary credentials. Do not configure long-term AccessKey credentials in metadata or user code.

### Image requirements for the second-generation runtime

If you use a custom template with the [second-generation runtime (MicroVM)](../02.Templates/08.Build%20and%20Manage%20Templates%20via%20OpenAPI.md), install ossfs2 2.0.9 or later in the source image before you build the template. The second-generation runtime uses the source image directly and does not inject ossfs2 during the template build. The current ossfs2 package supports only `linux/amd64`. The following Dockerfile uses Ubuntu 22.04 and ossfs2 2.0.9:

```dockerfile
FROM ubuntu:22.04

ARG DEBIAN_FRONTEND=noninteractive
ARG OSSFS2_DEB_URL=https://gosspublic.alicdn.com/ossfs/ossfs2_2.0.9_linux_x86_64.deb
ARG OSSFS2_DEB_SHA256=33b5d16e870f53680a595b6369fd34eda18928807bae5fd934940f079cc04f6e

RUN set -eux; \
    apt-get update; \
    apt-get install -y --no-install-recommends ca-certificates curl fuse3; \
    curl --fail --location --retry 3 \
        "${OSSFS2_DEB_URL}" \
        --output /tmp/ossfs2.deb; \
    echo "${OSSFS2_DEB_SHA256}  /tmp/ossfs2.deb" | sha256sum -c -; \
    apt-get install -y --no-install-recommends /tmp/ossfs2.deb; \
    rm -f /tmp/ossfs2.deb; \
    rm -rf /var/lib/apt/lists/*

WORKDIR /root
```

When the package is updated, update `OSSFS2_DEB_URL` and `OSSFS2_DEB_SHA256` together. Do not skip SHA-256 verification, and do not store storage credentials or mount configuration in the image.

Build and push the `linux/amd64` image:

```bash
docker buildx build \
  --platform linux/amd64 \
  --push \
  -t <registry>/<namespace>/microsandbox-ossfs2:2.0.9 \
  .
```

After the build is complete, verify that the image contains ossfs2 2.0.9 or later:

```bash
docker run --rm --platform linux/amd64 \
  <registry>/<namespace>/microsandbox-ossfs2:2.0.9 \
  sh -euxc '
    test -x /usr/local/bin/ossfs2
    installed_version="$(dpkg-query -W ossfs2 | cut -f2)"
    dpkg --compare-versions "${installed_version}" ge "2.0.9"
  '
```

This check validates only the image contents. It does not verify permissions, the endpoint, or an actual mount.

## Configure permissions

Attach the following permission policy to the function execution RAM Role. Restrict `Resource` to the actual read and write scope:

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "oss:GetObject",
        "oss:ListObjects",
        "oss:AbortMultipartUpload",
        "oss:CompleteMultipartUpload",
        "oss:DeleteObject",
        "oss:InitiateMultipartUpload",
        "oss:ListParts",
        "oss:PutObject",
        "oss:UploadPart",
        "oss:PutBucket"
      ],
      "Resource": "*"
    }
  ]
}
```

## Install the SDK

This topic uses the E2B Python SDK. `volume_mounts` requires E2B Python SDK 2.31.0 or later.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install "e2b>=2.31.0"
```

Set the following environment variables before running the example:

```bash
export E2B_API_KEY="<your-e2b-api-key>"
export E2B_API_URL="https://api.<region>.e2b.fc.aliyuncs.com"
export E2B_DOMAIN="<region>.e2b.fc.aliyuncs.com"
export E2B_TEMPLATE="<template-id>"

export AGENTIC_BUCKET_VOLUME_NAME="<volume-name>"
export FCSANDBOX_ROLE_ARN="acs:ram::<account-id>:role/<execution-role>"
```

## Mount and verify

The following example mounts the AgenticBucket Volume to `/mnt/agentic-bucket` and verifies file read/write. The Volume must not be read-only. Save the code as `03_mount_agentic_bucket_volume.py`:

```python
import os

from e2b import Sandbox


def require_env(name: str) -> str:
    value = os.environ.get(name, "").strip()
    if not value:
        raise RuntimeError(f"missing environment variable: {name}")
    return value


mount_dir = "/mnt/agentic-bucket"
marker_path = f"{mount_dir}/hello-agentic-bucket.txt"
sandbox = None

try:
    sandbox = Sandbox.create(
        template=require_env("E2B_TEMPLATE"),
        timeout=300,
        api_key=require_env("E2B_API_KEY"),
        api_url=require_env("E2B_API_URL"),
        domain=require_env("E2B_DOMAIN"),
        volume_mounts={
            mount_dir: require_env("AGENTIC_BUCKET_VOLUME_NAME"),
        },
        metadata={
            "fc.sandbox.auth.role": require_env("FCSANDBOX_ROLE_ARN"),
        },
    )

    sandbox.files.write(marker_path, "hello agentic bucket\n")
    content = sandbox.files.read(marker_path)
    if content != "hello agentic bucket\n":
        raise RuntimeError(f"AgenticBucket file content mismatch: {content!r}")
finally:
    if sandbox is not None:
        sandbox.kill()

print("AgenticBucket Volume mount read/write verification succeeded")
```

Run the example:

```bash
python 03_mount_agentic_bucket_volume.py
```

## Behavior

- `volume_mounts` uses the `{mount directory: Volume name}` format, not a Volume ID.
- When creating the sandbox, pass the execution Role through `fc.sandbox.auth.role`. You do not need to configure long-term AccessKey credentials in the sandbox.
- A sandbox restores the Volume mount after it is paused and resumed. BucketSpace data is independent of the sandbox lifecycle.

## Limits

- For same-region access, use the internal OSS endpoint in the region where the AgenticBucket resides. No additional VPC configuration is required.
- A single sandbox creation request can contain at most five AgenticBucket mount points.
- The mount directory must be a normalized absolute Unix path. It cannot be `/`, and it cannot contain leading or trailing whitespace or `..`.
- Mount directories in the same sandbox cannot be duplicated. We recommend `/mnt/agentic-bucket` or one of its subdirectories to avoid covering existing directories in the template.
- A read-only Volume can only read files under the mount path.

## FAQ

### Sandbox creation reports the `requires executionRoleArn` error

Check whether `fc.sandbox.auth.role` is empty and whether the Role's trust policy allows the Function Compute service to assume it.

### Sandbox mount fails on creation

Check whether the Volume and API key belong to the same Team, whether the AgenticBucket, BucketSpace, and endpoint match, and whether the execution Role has the required permissions. Keep the request ID for troubleshooting.

### The Volume is mounted but cannot be written to

Check whether the Volume is read-only, whether the execution Role has write permissions, and whether AgenticBucket access control denies access.
