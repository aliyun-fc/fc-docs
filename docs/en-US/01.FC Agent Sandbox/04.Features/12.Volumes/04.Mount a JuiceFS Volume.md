# Mount a JuiceFS Volume

When creating a sandbox, use `volume_mounts` to mount an existing JuiceFS Volume to a specified directory. The mounted JuiceFS data remains available after the sandbox is released.

To submit the complete JuiceFS configuration directly when creating a sandbox, see [Dynamically mount JuiceFS](../07.FC%20Extensions/12.Dynamic%20JuiceFS%20Mounts.md).

To append a mount to a running sandbox, see [Append Sandbox Storage Mounts](../07.FC%20Extensions/09.Append%20Sandbox%20Storage%20Mounts.md).

## Prerequisites

Before you begin, prepare the following resources and information:

- A [JuiceFS Volume](../07.FC%20Extensions/11.Create%20a%20JuiceFS%20Volume.md) has been created for the target Team, and its Volume name is available.
- An FC Agent Sandbox API key is bound to the same Team. Volumes and API keys cannot be used across Teams.
- A Virtual Private Cloud (VPC), vSwitch, and security group can connect to the JuiceFS service.
- The FC Agent Sandbox API URL, Domain, and a custom second-generation runtime (MicroVM) template are available.

### Second-generation runtime image requirements

JuiceFS Volume mounts require the [second-generation runtime (MicroVM)](../02.Templates/08.Build%20and%20Manage%20Templates%20via%20OpenAPI.md). Before building the custom template, install the JuiceFS Enterprise client, the RADOS runtime library, and FUSE 2 in the source image. The second-generation runtime uses the source image directly and does not inject the JuiceFS client during template builds.

Only JuiceFS Enterprise is supported. JuiceFS provides Enterprise Mount images in the [`juicedata/mount`](https://hub.docker.com/r/juicedata/mount/tags) repository on Docker Hub. Enterprise image tags start with `ee-`. In the image, `/usr/bin/juicefs` is a client launcher, and the fixed-version client executable is located at `/usr/local/juicefs/mount/jfsmount`.

The following example uses `juicedata/mount:ee-5.3.7-58af72b`, where `5.3.7` is the client version and `58af72b` is the build commit. Check version information against the [JuiceFS command reference](https://juicefs.com/docs/cloud/reference/command_reference/). For more information about images and containers, see [Use JuiceFS in Docker](https://juicefs.com/docs/cloud/use_juicefs_in_docker/).

First, pull the image and verify the Enterprise client:

```bash
docker pull --platform linux/amd64 \
  juicedata/mount:ee-5.3.7-58af72b

docker run --rm --platform linux/amd64 \
  --entrypoint /usr/bin/juicefs \
  juicedata/mount:ee-5.3.7-58af72b \
  version
```

The output must show client version `5.3.7` and build commit `58af72b`. Do not use floating tags such as `latest` or `ee-nightly`, because rebuilding the template could then change the client version. If your build environment cannot access Docker Hub, synchronize the image to an accessible private image registry and replace the `juicedata/mount` image address in the following Dockerfile.

The following Dockerfile uses Ubuntu 22.04 by default. To extend an existing Sandbox base image, pass its image address through the `BASE_IMAGE` build argument:

```dockerfile
ARG BASE_IMAGE=ubuntu:22.04

FROM juicedata/mount:ee-5.3.7-58af72b AS juicefs-ee

FROM ${BASE_IMAGE}

ARG DEBIAN_FRONTEND=noninteractive

RUN set -eux; \
    apt-get update; \
    apt-get install -y --no-install-recommends \
        ca-certificates \
        fuse \
        librados2; \
    rm -rf /var/lib/apt/lists/*

COPY --from=juicefs-ee /usr/local/juicefs/mount/jfsmount /usr/bin/juicefs

RUN set -eux; \
    chmod 0755 /usr/bin/juicefs; \
    command -v juicefs; \
    command -v fusermount; \
    mkdir -p /mnt/juicefs

WORKDIR /root

# Do not set a custom USER, ENTRYPOINT, or CMD. The sandbox control plane manages startup.
```

Do not store the JuiceFS token or mount configuration in the Dockerfile or image layers.

Build and push a `linux/amd64` image. Replace the placeholders with actual values:

```bash
docker buildx build \
  --platform linux/amd64 \
  --build-arg BASE_IMAGE="<your-sandbox-base-image>" \
  --push \
  -t "<registry>/<namespace>/microsandbox-juicefs-ee:<version>" \
  .
```

After the build is complete, verify the client, the RADOS runtime library, and FUSE 2 in the image:

```bash
docker run --rm --platform linux/amd64 \
  --entrypoint /bin/sh \
  <registry>/<namespace>/microsandbox-juicefs-ee:<version> \
  -euxc '
    command -v juicefs
    command -v fusermount
    ldconfig -p | grep "librados\.so\.2"
    juicefs version
  '
```

This check verifies only the image contents. It does not verify VPC connectivity, the token, or an actual mount. Rebuild the MicroVM template with this image before running the following example.

## Install the SDK

This guide uses the E2B Python SDK. `volume_mounts` requires E2B Python SDK 2.31.0 or later.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install "e2b>=2.31.0"
```

Set the following environment variables before running the example:

```bash
export E2B_API_KEY="<your-e2b-api-key>"
export E2B_API_URL="https://api.<region>.e2b.fc.aliyuncs.com"
export E2B_DOMAIN="<region>.e2b.fc.aliyuncs.com"
export E2B_TEMPLATE="<microvm-template-id>"

export JUICEFS_SANDBOX_VOLUME_NAME="juicefs-workspace"
export FCSANDBOX_VPC_ID="vpc-xxxxxxxx"
export FCSANDBOX_SECURITY_GROUP_ID="sg-xxxxxxxx"
export FCSANDBOX_VSWITCH_ID="vsw-xxxxxxxx"
```

## Mount and verify

The following example mounts a JuiceFS Volume to `/mnt/juicefs` and verifies file creation, reading, and deletion. Save the code as `04_mount_juicefs_volume.py`:

```python
import json
import os

from e2b import Sandbox


def require_env(name: str) -> str:
    value = os.environ.get(name, "").strip()
    if not value:
        raise RuntimeError(f"missing environment variable: {name}")
    return value


vpc_config = {
    "vpcId": require_env("FCSANDBOX_VPC_ID"),
    "securityGroupId": require_env("FCSANDBOX_SECURITY_GROUP_ID"),
    "vSwitchIds": [require_env("FCSANDBOX_VSWITCH_ID")],
}

mount_dir = "/mnt/juicefs"
marker_path = f"{mount_dir}/hello-juicefs.txt"
sandbox = None
marker_written = False

try:
    sandbox = Sandbox.create(
        template=require_env("E2B_TEMPLATE"),
        timeout=300,
        api_key=require_env("E2B_API_KEY"),
        api_url=require_env("E2B_API_URL"),
        domain=require_env("E2B_DOMAIN"),
        volume_mounts={
            mount_dir: require_env("JUICEFS_SANDBOX_VOLUME_NAME"),
        },
        metadata={
            "fc.sandbox.network.vpc": json.dumps(vpc_config),
        },
    )

    info = sandbox.get_info()
    print(f"volume_mounts={info.volume_mounts}")

    sandbox.files.write(marker_path, "hello juicefs\n")
    marker_written = True
    content = sandbox.files.read(marker_path)
    if content != "hello juicefs\n":
        raise RuntimeError(f"unexpected file content: {content!r}")
finally:
    try:
        if sandbox is not None and marker_written:
            sandbox.files.remove(marker_path)
    finally:
        if sandbox is not None:
            sandbox.kill()

print("JuiceFS Volume mount verified")
```

Run the example:

```bash
python 04_mount_juicefs_volume.py
```

## Behavior

- `volume_mounts` uses the `{mount directory: Volume name}` format. Do not use a Volume ID or JuiceFS file system name.
- The gateway resolves the Volume name to the `volumeName`, `baseURL`, `remoteDir`, `token`, and `args` stored during Volume creation, and then converts them to a JuiceFS mount configuration.
- This example provides the complete VPC configuration in `fc.sandbox.network.vpc` when the sandbox is created. The VPC configuration can also be stored in `mountConfig.vpcConfig` when the JuiceFS Volume is created. If both locations provide a VPC configuration, the sandbox creation request takes precedence.
- The JuiceFS Volume is remounted after a sandbox is paused and resumed. JuiceFS data is independent of the sandbox lifecycle.

## Limits

- A complete `vpcId`, `securityGroupId`, and non-empty `vSwitchIds` configuration must be available when the sandbox is created. The VPC configuration in the template cannot replace this mount configuration.
- The JuiceFS service address must be reachable from the VPC.
- The mount directory must be a normalized absolute Unix path. It cannot be `/` and cannot contain leading or trailing spaces or `..`.
- We recommend using a subdirectory of `/home`, `/mnt`, `/tmp`, or `/data`, such as `/mnt/juicefs`, to avoid overwriting an existing directory in the template.
- Mount directories cannot be duplicated in the same sandbox.
- A sandbox supports up to five JuiceFS mount points. When mounts are appended, the combined total of existing and new JuiceFS mount points cannot exceed five.
- Multiple JuiceFS Volumes in the same sandbox creation or append-mount request must use the same `baseURL`.
- If named Volumes and direct metadata JuiceFS mounts are used together, their service addresses must match.

## FAQ

### The Volume was created, but sandbox creation times out or the mount fails

Verify that the MicroVM image contains the JuiceFS Enterprise client, the RADOS runtime library, and FUSE 2. Also check the VPC routes, security group, JuiceFS service address, token, file system name, and remote directory. `CreateVolume` does not test network connectivity or perform a mount.

### Which name should be specified in `volume_mounts`?

Specify the name used when the FC Agent Sandbox Volume was created, which is `JUICEFS_SANDBOX_VOLUME_NAME` in this example. Do not specify the JuiceFS file system name or Volume ID.
