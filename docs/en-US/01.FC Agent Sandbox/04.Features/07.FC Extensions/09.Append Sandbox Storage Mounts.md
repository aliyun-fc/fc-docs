# Append Sandbox Storage Mounts

Use this API to append storage mounts to a running Sandbox without recreating it.

This API only supports appending mounts. It does not support deleting, replacing, or unmounting existing mounts. Do not treat it as a full-update API: omitting an existing mount from the request does not delete that mount, and submitting the same mount more than once returns `400`.

The storage types currently available to users are OSS, AgenticBucket, AgenticFS, and JuiceFS.

## API Information

```text
POST /sandboxes/{sandboxID}/fc-volume-mounts
```

Request headers:

| Header | Required | Description |
| --- | --- | --- |
| `X-API-Key` | Yes | Cloud sandbox API Key. |
| `Content-Type: application/json` | Yes | The request body is in JSON format. |

The API returns `204 No Content` with an empty response body upon success.

## Prerequisites

Before calling the API, make sure that:

- The Sandbox is in the `running` state. Resume a paused Sandbox before calling this API.
- The API Key and target Sandbox belong to the same Team.
- When using `namedVolumeMounts`, the referenced Volume has been created in the same Team and is available. Supported types include [OSS Volume](./07.Create%20an%20OSS%20Volume.md), [AgenticBucket Volume](../12.Volumes/03.Mount%20an%20AgenticBucket%20Volume.md), [AgenticFS Volume](./08.Create%20an%20AgenticFS%20Volume.md), and [JuiceFS Volume](./11.Create%20a%20JuiceFS%20Volume.md).
- When creating the Sandbox, you configured the execution Role and VPC required by the new storage through `createSandbox`. This API only appends mounts; it does not add or modify these configurations.

The following table lists the configurations required by each storage type when you call `createSandbox`:

| Storage type | Complete VPC configuration | Execution Role |
| --- | --- | --- |
| OSS | Not required | Required |
| AgenticBucket | Not required | Required |
| AgenticFS | Required | Required |
| JuiceFS | Required | Not required |

- If you plan to append an OSS or AgenticBucket mount, configure the execution Role through `fc.sandbox.auth.role` when calling `createSandbox`.
- If you plan to append an AgenticFS mount, in addition to the execution Role, configure a complete VPC through `fc.sandbox.network.vpc`. The configuration must include `vpcId`, `securityGroupId`, and `vSwitchIds` with at least one element. For details, see [VPC Network Configuration](./02.VPC%20Network%20Configuration.md).
- To append a JuiceFS mount, configure the same complete VPC through `fc.sandbox.network.vpc` when creating the Sandbox. Even if the JuiceFS Volume stores `mountConfig.vpcConfig`, an append request does not modify the VPC of the Function associated with the running Sandbox.

## Storage access permissions

An appended mount uses the execution Role configured when the Sandbox was created through `fc.sandbox.auth.role`. The request does not add to or expand the permissions of the execution Role. FC Agent Sandbox uses the Role to obtain temporary STS credentials and narrows the permissions based on the actual mount configuration:

- The OSS permission boundary is determined by the Bucket and `bucketPath`. For example, after mounting `/users/abc` from `oss-bucket1`, the credentials can access only that prefix; `oss:ListObjects` is restricted through `oss:Prefix`.
- The AgenticFS permission boundary is determined by the Access Point. The `serverAddr` subdirectory under the Access Point only determines the actual remote path and cannot replace Access Point-level isolation.

You only need to grant the execution Role the basic storage operations required by the mount. You do not need to manually configure fine-grained resource scopes for a Bucket, FileSystem, or Access Point. The system automatically generates the corresponding restrictions in the STS permissions based on the Volume configuration used at creation time or the inline mount configuration in this request.

For permission reminders when creating Volumes, see [Create an OSS Volume](./07.Create%20an%20OSS%20Volume.md) and [Create an AgenticFS Volume](./08.Create%20an%20AgenticFS%20Volume.md).

## Request Parameters

The request body supports inline mounts, existing Volumes, or both:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `inlineVolumeMounts` | object | Conditionally required | Declares the storage mount configuration directly. Currently supports `oss`, `agenticBucket`, `agenticFS`, and `juiceFS`. |
| `namedVolumeMounts` | array | Conditionally required | References existing Volumes in the current Team. Each item contains the Volume name in `name` and the mount path inside the Sandbox in `path`. |

You must provide at least one valid mount point in `inlineVolumeMounts` or `namedVolumeMounts`. An empty request or empty configuration returns `400`.

The following table describes the inline configuration fields. Field names are case-sensitive. Pay particular attention to `agenticFS` and the AgenticFS fields `userID` and `groupID`:

| Configuration | Field | Required | Constraints |
| --- | --- | --- | --- |
| `oss` | `mountPoints` | Yes | Contains 1 to 5 mount points in this request. Existing and new mounts combined cannot exceed five. |
| `oss` | `mountPoints[].bucketName` | Yes | 3 to 64 characters in length. |
| `oss` | `mountPoints[].bucketPath` | No | Path within the Bucket, up to 128 characters. Set it to `/` or leave it empty to specify the Bucket root directory. |
| `oss` | `mountPoints[].endpoint` | Yes | OSS Endpoint, up to 128 characters. It must match the region of the Bucket. |
| `oss` | `mountPoints[].mountDir` | Yes | Absolute path inside the Sandbox, 2 to 64 characters in length. It cannot be `/`. |
| `oss` | `mountPoints[].readOnly` | No | Specifies whether the mount is read-only. Boolean value. |
| `agenticBucket` | `mountPoints` | Yes | Contains 1 to 5 mount points in this request. Existing and new AgenticBucket mounts combined cannot exceed five. |
| `agenticBucket` | `mountPoints[].agenticBucket` | Yes | Full AgenticBucket name. |
| `agenticBucket` | `mountPoints[].bucketName` | Yes | Full BucketSpace name. |
| `agenticBucket` | `mountPoints[].bucketPath` | No | Path in the BucketSpace. Defaults to `/` if omitted. |
| `agenticBucket` | `mountPoints[].endpoint` | Yes | OSS endpoint that matches the AgenticBucket region. |
| `agenticBucket` | `mountPoints[].mountDir` | Yes | Absolute path inside the Sandbox. It cannot be `/`. |
| `agenticBucket` | `mountPoints[].readOnly` | No | Specifies whether the mount is read-only. Defaults to `false` if omitted. |
| `agenticFS` | `userID` | No | If specified, the value must be from `-1` to `65534` and match `agenticFS.userID` passed when the Sandbox was created. |
| `agenticFS` | `groupID` | No | If specified, the value must be from `-1` to `65534` and match `agenticFS.groupID` passed when the Sandbox was created. |
| `agenticFS` | `mountPoints` | Yes | Contains 1 to 5 mount points in this request. Existing and new mounts combined cannot exceed five. |
| `agenticFS` | `mountPoints[].serverAddr` | Yes | AgenticFS Access Point address, up to 128 characters. |
| `agenticFS` | `mountPoints[].mountDir` | Yes | Normalized absolute path inside the Sandbox, up to 128 characters. It cannot be `/`. |
| `juiceFS` | `envs` | No | Environment variables passed only to the JuiceFS mount process. If the Sandbox does not have a JuiceFS service address, provide `envs.BASE_URL`. |
| `juiceFS` | `envs.BASE_URL` | Conditionally required | Service address used by the JuiceFS Enterprise client. Existing and new JuiceFS mounts must use the same service address. |
| `juiceFS` | `mountPoints` | Yes | Contains 1 to 5 mount points in this request. Existing and new JuiceFS mounts combined cannot exceed five. |
| `juiceFS` | `mountPoints[].volumeName` | Yes | JuiceFS file system name, not an FC Agent Sandbox Volume name or ID. |
| `juiceFS` | `mountPoints[].remoteDir` | No | Remote directory in the JuiceFS file system. Explicitly setting this field is recommended. |
| `juiceFS` | `mountPoints[].mountDir` | Yes | Normalized absolute path inside the Sandbox. It cannot be `/`. |
| `juiceFS` | `mountPoints[].token` | Yes | Access token of the JuiceFS file system. |
| `juiceFS` | `mountPoints[].args` | No | Additional mount options passed to the JuiceFS client as an array of strings. The platform manages `--token` and `--subdir` based on `token` and `remoteDir`. Do not pass these options again in this field. |

## Local mount directory

`mountDir` in `inlineVolumeMounts` and `namedVolumeMounts[].path` specify a local filesystem mount point inside the Sandbox runtime, not a remote storage directory.

- We recommend a subdirectory of `/home`, `/mnt`, `/tmp`, or `/data`, such as `/mnt/oss`, `/mnt/agenticfs`, or `/data/files`, to avoid covering existing directories in the template.
- Common Linux and Unix system directories and their subdirectories cannot be used as mount points. Examples include `/bin`, `/opt`, `/var`, `/dev`, and subdirectories such as `/opt/data` and `/var/data`. Using these paths can cause the mount to fail.
- **Mount paths do not support hidden files or directories (names beginning with `.`), such as `/root/.cache` and `/home/user/.cache`.** Even under a recommended directory such as `/home`, the path cannot contain a hidden directory such as `.cache`. To access mounted content through a hidden directory, first mount the storage at a supported path, then use `ln -s` to create a symbolic link pointing to that mount directory.

## Append an Existing Volume

The following example appends an existing Volume to a running Sandbox:

```bash
export E2B_API_KEY="<your-e2b-api-key>"
export E2B_API_URL="https://api.<region>.e2b.fc.aliyuncs.com"
export SANDBOX_ID="<sandbox-id>"

curl --include --request POST \
  "${E2B_API_URL}/sandboxes/${SANDBOX_ID}/fc-volume-mounts" \
  --header "X-API-Key: ${E2B_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{
    "namedVolumeMounts": [
      {
        "name": "oss-workspace",
        "path": "/mnt/oss"
      }
    ]
  }'
```

Use the Volume name, not the Volume ID, for `name`. `path` must be a normalized absolute Unix path. It cannot be `/`, contain leading or trailing spaces, or contain `.` or `..` path segments.

## Append an Inline Mount

### OSS

The following example directly appends a read-only OSS mount:

```bash
curl --include --request POST \
  "${E2B_API_URL}/sandboxes/${SANDBOX_ID}/fc-volume-mounts" \
  --header "X-API-Key: ${E2B_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{
    "inlineVolumeMounts": {
      "oss": {
        "mountPoints": [
          {
            "bucketName": "example-bucket",
            "bucketPath": "/datasets",
            "endpoint": "oss-cn-hangzhou.aliyuncs.com",
            "mountDir": "/mnt/datasets",
            "readOnly": true
          }
        ]
      }
    }
  }'
```

The execution Role used for the OSS mount must be included in the `createSandbox` request that creates the Sandbox, must already be in effect, and must have permission to access the target Bucket path. For details about fields and permission configuration, see [Dynamic OSS Mounts](./04.Dynamic%20OSS%20Mounts.md).

### AgenticBucket

To append an AgenticBucket mount, place the configuration in `inlineVolumeMounts.agenticBucket`. For example:

```bash
curl --include --request POST \
  "${E2B_API_URL}/sandboxes/${SANDBOX_ID}/fc-volume-mounts" \
  --header "X-API-Key: ${E2B_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{
    "inlineVolumeMounts": {
      "agenticBucket": {
        "mountPoints": [
          {
            "agenticBucket": "<agentic-bucket-full-name>",
            "bucketName": "<bucket-space-full-name>",
            "bucketPath": "/",
            "endpoint": "<oss-endpoint>",
            "mountDir": "/mnt/agentic-bucket",
            "readOnly": false
          }
        ]
      }
    }
  }'
```

You can also combine inline mounts and existing Volumes in the same request:

```json
{
  "inlineVolumeMounts": {
    "agenticFS": {
      "userID": 1000,
      "groupID": 1000,
      "mountPoints": [
        {
          "serverAddr": "ap-<access-point-id>.<file-system-id>-<suffix>.<region>.nas.aliyuncs.com:/",
          "mountDir": "/mnt/agenticfs"
        }
      ]
    }
  },
  "namedVolumeMounts": [
    {
      "name": "oss-workspace",
      "path": "/mnt/oss"
    }
  ]
}
```

### JuiceFS

To append an inline JuiceFS mount, place the configuration in `inlineVolumeMounts.juiceFS`. The Function must already have a complete VPC configuration:

```bash
curl --include --request POST \
  "${E2B_API_URL}/sandboxes/${SANDBOX_ID}/fc-volume-mounts" \
  --header "X-API-Key: ${E2B_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{
    "inlineVolumeMounts": {
      "juiceFS": {
        "envs": {
          "BASE_URL": "https://<juicefs-service-address>"
        },
        "mountPoints": [
          {
            "volumeName": "<juicefs-file-system-name>",
            "remoteDir": "/datasets/project-a",
            "mountDir": "/mnt/juicefs",
            "token": "<juicefs-token>",
            "args": []
          }
        ]
      }
    }
  }'
```

`remoteDir` is the remote directory in JuiceFS, whereas `mountDir` is the local directory in the Sandbox. The platform converts `remoteDir` to the JuiceFS client option `--subdir`. Do not specify this option again in `args`. For field descriptions and image requirements, see [Dynamically mount JuiceFS](./12.Dynamic%20JuiceFS%20Mounts.md).

## Verify the Mounts

A `204` response means that the append request was accepted; it does not prove that data I/O through the mount succeeded. Once the Sandbox is available, check mount visibility, state, and object I/O separately:

1. Call `GET /sandboxes/{sandboxID}`. Mounts appended through `namedVolumeMounts` appear in `volumeMounts` in the response, whereas inline mounts do not.
2. Read a known, existing object that is safe to access through the mount. Directory listing and object I/O are separate observations: a listing failure alone does not prove mount I/O failed, and a successful listing does not prove objects can be read or written. Behavior without List permission may vary by storage type, runtime, and release; do not assume every release supports a usable no-List workflow.
3. Only for a writable mount, write a unique test object in a safe location, flush, fsync, and close it, then reopen it and read it back. Do not overwrite business data. For a read-only mount, perform reads only and do not write.
4. If an append fails, before sending a new request, check the Sandbox mount state and verify reads and other permitted I/O on existing mounts. After correcting a confirmed Role, target, or client issue, send a deliberate new request under the existing API contract, then verify object I/O through both existing and new paths. An append failure does not mean it was rolled back; do not retry blindly or assume repeated requests are idempotent.

## Behavior and Limits

- This API only appends mounts. It does not support deleting, replacing, or unmounting them. To remove a mount, release and recreate the Sandbox.
- A single request can append multiple storage types, but every new mount directory must be unique and cannot conflict with an existing mount directory in the current Sandbox.
- If you specify `userID` or `groupID` for AgenticFS, it must match `agenticFS.userID` or `agenticFS.groupID` passed when the Sandbox was created.
- Quotas are validated against the combined total of existing and new mounts in the current Sandbox. OSS, AgenticBucket, AgenticFS, and JuiceFS each support up to five mount points. Even if the current request does not exceed the limit on its own, the combined total may exceed the limit because of existing Sandbox mounts and result in a `400` response.
- Do not concurrently update mounts for the same Sandbox. Duplicate, overlapping, or concurrent conflicting requests return `400`.

## Common Errors

### Self-service troubleshooting by diagnostic code

If the response `Message` contains one of the exact bracketed diagnostic codes below, use the corresponding checklist. A code is a best-effort hint based on limited signals; it can be inaccurate or absent and does not prove the root cause. It does not replace the original HTTP status, FC `Code`, or retry behavior. If no code or an unknown code is present, use the general checklist under `STORAGE_MOUNT_FAILED`. Values such as `243` and `521` are client exit information, not HTTP or FC error codes, and are not necessarily exposed by the API. A `403`, `AccessDenied`, or `EACCES` can also be related to credentials, a Bucket Policy, a prefix, or a specific operation; none alone proves a RAM root cause.

#### `[OSS_PERMISSION_ERROR]`

- **Meaning:** OSS access may be restricted; this does not confirm that a RAM policy denied the request.
- **Possible causes:** The execution Role lacks the required operation permission, its trust relationship does not allow FC to obtain credentials, a Bucket Policy or condition explicitly denies access, the object prefix does not match, or temporary credentials are invalid.
- **Checks, from lower to higher cost:**
  1. Identify whether the failed operation was reading a known object, writing an object, or listing a directory; check the Bucket, `bucketPath`, and `readOnly`. `GetObject` (read an object), `PutObject` (write an object), and `ListObjects` (list objects) are separate operations. A listing failure only indicates a listing failure; it does not establish that object reads or writes failed.
  2. Confirm that `fc.sandbox.auth.role` set when the Sandbox was created is the expected Role. Ask its administrator to check whether the trust relationship allows FC to obtain credentials. A trust relationship that permits credential retrieval does not itself grant OSS operation permissions.
  3. Ask the administrator to inspect the Role and target Bucket policies for the exact operation, Bucket, object prefix, and `oss:Prefix` condition. An explicit `Deny` in a Bucket Policy or its conditions can override an allow in another policy.
  4. Grant permissions only if a missing permission is confirmed: `oss:GetObject` for reads under the required object prefix; `oss:PutObject` for required writes on a writable mount; and `oss:ListObjects`, constrained by `oss:Prefix`, when client initialization or the workflow requires listing. Some clients list during initialization even if the guest does not list a directory. Do not grant wildcard `oss:*` or expand access to unrelated Buckets or prefixes.
- **Verify after fixing:** Test the required object read and directory listing separately. Only on a writable mount, write a unique test object in a safe location, then flush, fsync, close, reopen, and read it back. Do not write to a read-only mount.

#### `[OSS_CREDENTIAL_ERROR]`

- **Meaning:** OSS temporary credentials may be invalid or expired; this does not confirm credentials as the root cause.
- **Possible causes:** The execution Role was misconfigured when the Sandbox was created, its trust relationship changed, or the credential provider chain could not obtain or refresh valid temporary STS credentials.
- **Checks, from lower to higher cost:**
  1. Confirm that the execution Role configured when the Sandbox was created is the expected Role; an append request does not replace the Role or expand its permissions.
  2. Ask the Role administrator to check its trust relationship. Then use the supported credential provider to check temporary credential expiry and refresh status without copying, printing, or sending any AK, Token, or STS credential.
  3. Refresh temporary credentials through the supported flow for that provider. If the current Sandbox cannot obtain refreshed credentials, follow the product-supported Sandbox lifecycle to reconfigure or create one. Do not put a Token into the request or blindly repeat the append.
  4. If credentials are valid but the failure remains, follow `OSS_PERMISSION_ERROR` to check target permissions and the Bucket Policy. A tool's `Invalid Credentials` message can also accompany an actual access denial.
- **Verify after fixing:** After the credential provider confirms refresh, read a known object through the mount. On a writable mount, also verify a unique test object can be written and read back safely. A successful control-plane request does not prove valid credentials or data-plane I/O.

#### `[OSS_TARGET_ERROR]`

- **Meaning:** The OSS Bucket or Endpoint may be configured incorrectly.
- **Possible causes:** The Bucket name or region is wrong, the Endpoint does not match the Bucket's actual region, or the target Bucket does not exist.
- **Checks, from lower to higher cost:**
  1. Check the configured Bucket name and `bucketPath` against the intended target, including the object prefix.
  2. Confirm the Bucket's actual region and that the configured OSS Endpoint is for that region; do not infer the region from an error message alone.
  3. Use an authorized storage-management interface to confirm the target Bucket exists and is the intended one. If you cannot confirm it, ask the Bucket administrator instead of switching to another Bucket.
- **Verify after fixing:** After correcting a confirmed name, region, or Endpoint, read a known object through the mount. Only on a writable mount, separately verify writing and reading back a unique test object.

#### `[STORAGE_NETWORK_ERROR]`

- **Meaning:** The mount may have been unable to reach the storage Endpoint.
- **Possible causes:** The Endpoint name cannot be resolved, DNS is misconfigured, network routing or egress is restricted, or the connection timed out. A timeout alone does not prove a network root cause.
- **Checks, from lower to higher cost:**
  1. Check the Bucket region and Endpoint spelling.
  2. From the network where the Sandbox runs, check DNS resolution and connectivity to that Endpoint; then check applicable VPC, routing, and egress rules.
  3. If DNS or connectivity fails, ask the network administrator to correct the relevant resolution, route, or egress rule. Do not try to fix a network failure by broadening OSS permissions.
- **Verify after fixing:** Confirm that the Endpoint resolves and is reachable, then read a known object to verify I/O. Only on a writable mount, also verify a unique test object can be written and read back.

#### `[STORAGE_MOUNT_FAILED]`

- **Meaning:** A mount failure was identified, but there was not enough evidence to classify it further; this is a generic fallback with a troubleshooting checklist.
- **Possible causes:** Storage configuration, the execution Role, the target Bucket or Endpoint, credentials, network connectivity, or another mount-stage condition.
- **Checks, from lower to higher cost:**
  1. Confirm the Sandbox state, storage type, mount path, and operation. A failed append does not prove that the new mount was rolled back or that existing mounts stopped working.
  2. Check the documentation for that storage type and verify the Bucket/prefix, region/Endpoint, `readOnly`, and execution Role configured when the Sandbox was created.
  3. Check directory listing, reading a known object, and writing a new object separately. Without List permission, listing failure alone does not prove object reads or writes failed, and not every storage type, runtime, or release is guaranteed to support a usable no-List workflow.
  4. Correct only a confirmed problem. Before sending a new append request, check the Sandbox and existing mount state; do not retry blindly.
- **Verify after fixing:** Read a known object within the mount's permissions. Only on a writable mount, use a unique safe test object and flush, fsync, close, reopen, and read it back. Do not overwrite business data.

If these checks do not resolve the issue, contact product support. For direct FC calls, provide the actual HTTP status, FC `Code`, `Message`, and `RequestId` from the same response. For Gateway calls, provide the `RequestId` in the Gateway response; follow the product support process to correlate an FC `RequestId` from the same request. You may also provide the operation, entry point, region, and time. Do not send AKs, STS credentials, Tokens, SDK Data, or raw logs.



| Status code | Possible cause | Resolution |
| --- | --- | --- |
| `400` | Invalid JSON, no valid mount points, invalid fields or paths, duplicate mount directories, or too many mounts | Check the case of request body fields, mount paths, and the combined mount count. |
| `401` | No valid API Key was provided | Check the `X-API-Key` request header. |
| `403` | The API Key may not be authorized to call this API, or storage access may be restricted; the status alone does not confirm a RAM root cause | Check the API Key Action, execution Role, credentials, and storage-side permissions separately; use the diagnostic-code checklist above. |
| `404` | The Sandbox or named Volume does not exist or does not belong to the current Team | Check the Sandbox ID, Volume name, and the Team to which the API Key belongs. |
| `409` | The Sandbox is not running, the required VPC or execution Role was not provided through `createSandbox`, or the UID/GID conflicts with the current Sandbox | Resume the Sandbox. If configuration is missing, recreate the Sandbox and provide the required configuration through `createSandbox`. |
| `503` | Storage declarations or other dependencies are temporarily unavailable | Retain the request correlation information and contact product support. |
For direct FC calls, complete the checks above before providing product support with the actual HTTP status, FC `Code`, `Message`, and `RequestId` from the same response. For Gateway calls, provide the `RequestId` actually returned by the Gateway response. To correlate an FC `RequestId`, follow the product support process with same-request details; do not treat the two IDs as interchangeable. For unlisted 5xx responses, retain the actual response and contact product support; do not infer an unverified cause from a status code or internal text.
