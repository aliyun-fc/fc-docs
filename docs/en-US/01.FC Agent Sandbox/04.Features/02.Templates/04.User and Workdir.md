# User and Workdir

The user and working directory inside a template affect command execution, file permissions, and dependency installation paths. In agent scenarios, keep the working directory stable so commands do not rely on implicit paths.

## Check the current user and directory

```typescript
const result = await sandbox.commands.run("whoami && pwd");
console.log(result.stdout);
```

Python example:

```python
result = sandbox.commands.run("whoami && pwd")
print(result.stdout)
```

## Set the command working directory

```typescript
await sandbox.files.makeDir("/tmp/project");
await sandbox.files.write("/tmp/project/main.py", "print('hello')\n");

const result = await sandbox.commands.run("python3 main.py", {
  cwd: "/tmp/project",
});

console.log(result.stdout.trim());
```

Python example:

```python
sandbox.files.make_dir("/tmp/project")
sandbox.files.write("/tmp/project/main.py", "print('hello')\n")

result = sandbox.commands.run(
    "python3 main.py",
    cwd="/tmp/project",
)

print(result.stdout.strip())
```

## Default user and UID (second-generation runtime)

The default user of a template is `user`, and the default working directory is `/home/user`. You can also set them in the template `steps` (see "Custom default user and working directory" below). The platform ensures that this account exists and is usable inside the sandbox:

- The UID/GID is 1000 when available. If 1000 is already taken by another account in the image (for example `ubuntu` in `ubuntu:24.04` or `node` in the `node` image), the platform uses the next available UID such as 1001 or 1002 instead; the sandbox still starts.
- If the image already contains a `user` account, the platform uses that account and its UID.
- The platform prepares the owner of the default home directory (default `/home/user`): the directory is created if missing, and if it exists the directory and its contents are changed to be owned by the default user so that they are writable by default. This applies only to the default home directory; paths elsewhere in the image keep their owner, so a directory such as `/srv/app` owned by an account from the image or by root may still not be writable by `user`. Fix the ownership in the Dockerfile, or use `sudo` in the command.
- `commands.run`, the start command, and the ready command run as `user` by default, and the `cwd` of `commands.run` can be overridden per call. Check the actual identity in a sandbox with `sandbox.commands.run("id")`.
- If UID 1000 belongs to an application account in the image that owns the application files, and the application runs as `user`, `user` may not have write permission on those files. Fix the ownership in the Dockerfile.
- Do not hard-code UID 1000 in `chown`, sudoers, configuration files, or paths. Identify the account by the user name `user`, and use `$HOME` or `/home/user` for writable directories.

## Custom default user and working directory

Second-generation templates can declare `USER` and `WORKDIR` in `runtimeConfig.sandboxConfig.steps` of the POP OpenAPI `CreateTemplate`. The build creates the account and directory, and the sandbox default identity and working directory come from the last `USER` / `WORKDIR`:

```json
{
  "name": "my-template",
  "teamId": "<your-team-id>",
  "runtimeConfig": {
    "cpu": 2,
    "memorySize": 2048,
    "diskSize": 15360,
    "sandboxConfig": {
      "generation": 2,
      "image": "registry-vpc.cn-shanghai.aliyuncs.com/example/app:v1",
      "steps": [
        {"type": "USER", "args": ["app"]},
        {"type": "WORKDIR", "args": ["/home/app"]}
      ]
    }
  }
}
```

- `args[0]` of `USER` is the account name. If the account does not exist, it is created during the build; `commands.run`, the start command, and the ready command then run as that account.
- `args[0]` of `WORKDIR` is the working directory. Declaring only `USER` does not change the working directory; declare `WORKDIR` as well when you need a non-default directory.
- Without `USER`/`WORKDIR`, the defaults are `user` / `/home/user`.
- The OCI `USER` of the image (what a Dockerfile `USER` produces) does not take part in resolving the default identity and has no effect. Declare a `USER` step explicitly when you migrate from a Dockerfile.
- This capability is currently available only on the POP OpenAPI `CreateTemplate`. Passing `steps` inline in an E2B Template definition still returns `400 steps are not supported`, so `set_user`/`set_workdir` from the E2B SDK must be rewritten as POP steps.
- Build-time `steps` are supported only on the second-generation runtime; the first generation returns 400 when `steps` is passed. `COPY` is not supported yet.

## Recommendations

- Pin common tools and dependencies during template build.
- Use an explicit `cwd` when running tasks.
- Do not assume every image has the same default user, HOME directory, or permissions.
- Do not assume the default user always has UID 1000; include a `user` account in the image if you need a fixed UID.
