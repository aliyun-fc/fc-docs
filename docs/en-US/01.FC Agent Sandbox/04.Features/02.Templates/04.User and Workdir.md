# User and Workdir

The user and working directory inside a template affect command execution, file permissions, and dependency installation paths. In agent scenarios, keep the working directory stable so commands do not rely on implicit paths.

## Check the current user and directory

```typescript
const result = await sandbox.commands.run("whoami && pwd");
console.log(result.stdout);
```

Python example:

```python
result = sandbox.commands.run("whoami && pwd")
print(result.stdout)
```

## Set the command working directory

```typescript
await sandbox.files.makeDir("/tmp/project");
await sandbox.files.write("/tmp/project/main.py", "print('hello')\n");

const result = await sandbox.commands.run("python3 main.py", {
  cwd: "/tmp/project",
});

console.log(result.stdout.trim());
```

Python example:

```python
sandbox.files.make_dir("/tmp/project")
sandbox.files.write("/tmp/project/main.py", "print('hello')\n")

result = sandbox.commands.run(
    "python3 main.py",
    cwd="/tmp/project",
)

print(result.stdout.strip())
```

## Default user and UID

The default user of a template is `user`, and the default working directory is `/home/user`. You can also set them in the template `steps` (see "Custom default user and working directory" below). The platform ensures that this account exists when the sandbox starts:

- The UID/GID is 1000 when available. If 1000 is already taken by another account in the image (for example, `ubuntu` in `ubuntu:24.04` or `node` in the `node` image), the platform uses the next available UID such as 1001 or 1002 instead; the sandbox still starts.
- If the image already contains a `user` account, the platform uses that account and its UID, and keeps the existing owner of the account home directory.
- `commands.run`, the start command, and the ready command run as `user` by default. You can check the actual UID in a sandbox with `sandbox.commands.run("id")`.
- The `cwd` and `user` arguments of `commands.run` override the template defaults for that call. When omitted, the template default user and working directory apply. The start and ready commands cannot be overridden per call and always use the template defaults.
- If UID 1000 belongs to an application account in the image that owns the application files, and the application runs as `user`, `user` may not have write permission on those files. Fix the ownership in the Dockerfile or use `sudo` in the command.
- Do not hard-code UID 1000 in `chown`, sudoers, configuration files, or paths. Identify the account by the user name `user`, and use `$HOME` or `/home/user` for writable directories.
- `/etc/passwd` and `/etc/group` in the image must be standard files and writable. Otherwise, the platform cannot create or correct the default user and the sandbox fails to start.

## Custom default user and working directory

Templates of the second generation can declare `USER` and `WORKDIR` in `runtimeConfig.sandboxConfig.steps`. The build creates the account and directory, and after the sandbox starts, `commands.run`, the start command, and the ready command all run as that user in that directory:

```json
{
  "runtimeConfig": {
    "sandboxConfig": {
      "image": "registry-vpc.cn-shanghai.aliyuncs.com/example/app:v1",
      "steps": [
        {"type": "USER", "args": ["app"]},
        {"type": "WORKDIR", "args": ["/home/app"]}
      ]
    }
  }
}
```

- `args[0]` of `USER` is the account name. If the account does not exist, it is created during the build with its home directory as the primary home.
- `args[0]` of `WORKDIR` is the working directory. If it does not exist, it is created during the build and owned by that user.
- Without `USER`/`WORKDIR`, the defaults are `user` / `/home/user`.
- The OCI `USER` of the image (what a Dockerfile `USER` produces) is ignored and does not take part in resolving the default identity. Declare a `USER` step explicitly when you migrate an image.
- Build-time `steps` are supported only on the second generation (micro). The first generation returns 400 when `steps` is passed. `COPY` is not supported yet.

## Recommendations

- Pin common tools and dependencies during template build.
- Use an explicit `cwd` when running tasks.
- Do not assume every image has the same default user, HOME directory, or permissions.
- Do not assume the default user always has UID 1000; include a `user` account in the image if you need a fixed UID.
