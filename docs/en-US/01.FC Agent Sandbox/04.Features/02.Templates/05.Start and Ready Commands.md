# Start and Ready Commands

The start command and ready command are executed during the template build. They bake long-lived processes such as web services into the template:

1. During the build, the platform runs the start command as a background process, then repeatedly runs the ready command until it exits with code 0, which marks the service as ready.
2. Once the service is ready, the platform snapshots the still-running sandbox into the template. Sandboxes created from this template start with the service already running and are immediately accessible; the start command is not executed again.

If a process does not need to be baked into the template—for example, when each sandbox runs a different task—skip the template commands and run a background command after creating the sandbox instead. See "Run background commands in a sandbox" below.

## Limits

- Only templates on the second-generation runtime support start and ready commands. Setting either command on a first-generation template returns 400. The second-generation runtime requires whitelisting; see [Use the second-generation runtime](08.Build%20and%20Manage%20Templates%20via%20OpenAPI.md#use-the-second-generation-runtime).
- The ready command is considered successful the first time it exits with code 0, and waiting for readiness has a 5-minute hard timeout. If the start command exits early, the ready command keeps failing, or the wait times out, the template build fails; check the build logs for the cause.
- Without a ready command, the platform determines readiness with the default port probing; an explicit ready command takes precedence over it. A miswritten ready command surfaces as a build readiness timeout rather than a request parameter error, so verify the command inside the image first.
- When deriving a build from an existing template with `from_template`, you cannot set the start or ready command; the derived template inherits the base template's start command.

## Usage example

Create a second-generation template with the start and ready commands through the OpenAPI (POP SDK), then create a sandbox with the E2B SDK after the build is ready. For TypeScript, Go, and Java, see "Use the second-generation runtime" in [Build and Manage Templates via OpenAPI](08.Build%20and%20Manage%20Templates%20via%20OpenAPI.md).

Complete Python example (build a template with a preinstalled HTTP service, wait for port 8000, then create a sandbox and access the service):

```python
import os
import time

from alibabacloud_fcsandbox20260509 import models
from alibabacloud_fcsandbox20260509.client import Client as FCSandboxClient
from alibabacloud_tea_openapi import models as open_api_models
from e2b import Sandbox

REGION = "cn-hangzhou"
TEAM_ID = "<your-team-id>"  # See the prerequisites in "Build and Manage Templates via OpenAPI".

config = open_api_models.Config(
    access_key_id=os.environ["ALIBABA_CLOUD_ACCESS_KEY_ID"],
    access_key_secret=os.environ["ALIBABA_CLOUD_ACCESS_KEY_SECRET"],
    region_id=REGION,
    endpoint=f"fcsandbox.{REGION}.aliyuncs.com",
)
pop_client = FCSandboxClient(config)

# 1. Create a second-generation template and submit the build, baking the HTTP
#    service into the template.
resp = pop_client.create_template(
    models.CreateTemplateRequest(
        body=models.CreateTemplateInput(
            name=f"my-service-{int(time.time())}",
            team_id=TEAM_ID,
            runtime_config=models.CreateTemplateRuntimeConfig(
                # Second-generation templates default to a 60 GiB disk, which
                # requires at least 16 CPU cores; set a smaller disk for smaller specs.
                cpu=2,
                memory_size=2048,
                disk_size=15360,
                sandbox_config=models.CreateTemplateSandboxConfig(
                    image=f"fc-e2b-registry.{REGION}.cr.aliyuncs.com/runtime/base:v0.0.52",
                    # Start and ready commands are supported only on the second-generation runtime.
                    generation=2,
                    # The start command runs as a background process during the build.
                    start_command="python3 -m http.server 8000",
                    # The ready command runs repeatedly until it exits with code 0.
                    ready_command="curl -sf http://localhost:8000/ > /dev/null",
                ),
            ),
        )
    )
)
template_id = resp.body.template_id

# 2. Poll the build status until the template is ready.
deadline = time.time() + 900
while True:
    got = pop_client.get_template(template_id, models.GetTemplateRequest(team_id=TEAM_ID))
    state = got.body.status.state
    if state == "ready":
        break
    if state == "error":
        raise SystemExit(f"Build failed: {got.body.status.reason.message}")
    if time.time() > deadline:
        raise SystemExit("Build timed out")
    time.sleep(10)

# 3. The template snapshot already contains the running service, so the sandbox
#    is accessible immediately after creation.
sandbox = Sandbox.create(
    template=template_id,
    timeout=600,
    # The SDK reads E2B_API_KEY / E2B_API_URL / E2B_DOMAIN from the environment;
    # you can also pass api_url and domain explicitly per region.
    api_url=f"https://api.{REGION}.e2b.fc.aliyuncs.com",
    domain=f"{REGION}.e2b.fc.aliyuncs.com",
)
try:
    host = sandbox.get_host(8000)
    print(f"https://{host}")
finally:
    sandbox.kill()
```

Delete templates that are no longer needed: `pop_client.delete_template(template_id, models.DeleteTemplateRequest(team_id=TEAM_ID))`.

## Run background commands in a sandbox

For long-lived processes that do not need to be baked into a template, start them with a background command after creating the sandbox.

Python example:

```python
server = sandbox.commands.run(
    "python3 -m http.server 8000",
    background=True,
)

host = sandbox.get_host(8000)
print(f"https://{host}")
```

TypeScript example:

```typescript
const server = await sandbox.commands.run("python3 -m http.server 8000", {
  background: true,
});

const host = sandbox.getHost(8000);
console.log(`https://${host}`);
```
