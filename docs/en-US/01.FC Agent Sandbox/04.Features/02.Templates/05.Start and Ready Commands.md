# Start and Ready Commands

The start command and ready command are executed during the template build. They bake long-lived processes such as web services into the template:

1. During the build, the platform runs the start command as a background process in the sandbox and runs the ready command repeatedly until that command exits with code 0, which marks the service as ready. The two commands run concurrently and have no strict ordering.
2. Once the service is ready, the platform snapshots the still-running sandbox into the template. Sandboxes created from this template start with the service already running and are immediately accessible; the start command is not executed again.

If a process does not need to be baked into the template—for example, when each sandbox runs a different task—skip the template commands and run a background command after creating the sandbox instead. See "Run background commands in a sandbox" below.

## Limits

- Only templates on the second-generation runtime support start and ready commands. Setting either command on a first-generation template returns 400.
- The ready command is considered successful the first time it exits with code 0. Until then the platform runs it repeatedly for at most 5 minutes; exceeding that timeout fails the template build.
- The exit code of the start command does not take part in the readiness decision: if it exits early, including with a non-zero code, the build is not failed on that alone. If the service therefore never starts, the ready command keeps failing and the build eventually fails on the 5-minute timeout; the reported cause may point at either the start command or the readiness timeout.
- Readiness depends only on the exit code and stdout is not returned. The stderr of the last failed attempt is included in the build failure reason, so you can print diagnostics from the ready command with `exec 1>&2`.

## Execution user and environment

The following applies to sandboxes with `os_type=linux-amd64`. The platform runs the start and ready commands inside the build sandbox. Their identity comes from the template defaults and does not depend on the `USER` declared by the image:

- **Identity**: the template default user, `user`. This identity is not configurable today. It is not root and does not follow the image `USER`. If you are not sure, run `id` in the command first.
- **sudo prerequisite**: to run a command as root, prefix it with `sudo`, for example `sudo -E <command>`; `-E` preserves environment variables. Passwordless sudo comes from the image, not from the platform: the official base images already contain `/etc/sudoers.d/user` (`user ALL=(ALL) NOPASSWD:ALL`). A custom image must install `sudo` and add the same entry, otherwise you get `sudo: command not found` or a password prompt.
- **Working directory**: the template default working directory is `/home/user`. Use absolute paths in the commands instead of relying on the current directory.
- **UID assignment**: the UID/GID of `user` is 1000 when available. If 1000 is already taken by another account in the image (for example `ubuntu` in `ubuntu:24.04` or `node` in the `node` image), the platform uses the next available ID, usually 1001, and the sandbox still starts. Identify the account by the user name `user`, and do not hard-code the UID.
- **File ownership**: the platform prepares the owner of the default home directory (default `/home/user`); the directory and its contents belong to the default user so that it is writable by default. Paths elsewhere in the image keep their owner, so a directory such as `/srv/app` owned by an account from the image or by root may still not be writable by `user`. Fix the ownership in the image, or use `sudo` in the command.
- **systemd**: `systemctl` must run as root; without `sudo` it fails with `Failed to connect to system scope bus`. The image OCI `ENV` reaches only envd and the command processes it spawns (`commands.run`, the start command, the ready command); it does not reach systemd or the services systemd starts. Add a systemd drop-in that uses `EnvironmentFile=`, or run `sudo -E systemctl import-environment <VAR1> <VAR2>` in the start command and then restart the service.
- **Image entrypoint**: a second-generation sandbox uses systemd as PID 1, so the image `ENTRYPOINT`/`CMD` is not executed. Start long-running services from a systemd unit or from the start command.
- **Writable paths**: use locations writable by the default user, such as `$HOME` and `/tmp` (by default `$HOME=/home/user`). Do not assume that `/root`, `/var`, or another account's home directory is writable.
- **No manual backgrounding**: the platform already runs the start command in the background, so a foreground long-running process such as `python3 -m http.server 8000` is the recommended form; do not add `nohup` or `&` yourself.
- **Build-time side effects**: filesystem and systemd changes made during the build are captured in the template snapshot, including files under `/tmp` and `$HOME` and the result of `systemctl disable`. Do not leave debug logs, temporary files, or secrets in the image.

For troubleshooting steps, see [First generation works, second generation fails](08.Build%20and%20Manage%20Templates%20via%20OpenAPI.md#first-gen-works-second-gen-fails).

## Usage example

Create a second-generation template with the start and ready commands through the OpenAPI (POP SDK), then create a sandbox with the E2B SDK after the build is ready. For TypeScript, Go, and Java, see "Use the second-generation runtime" in [Build and Manage Templates via OpenAPI](08.Build%20and%20Manage%20Templates%20via%20OpenAPI.md).

Complete Python example (build a template with a preinstalled HTTP service, wait for port 8000, then create a sandbox and access the service):

```python
import os
import time

from alibabacloud_fcsandbox20260509 import models
from alibabacloud_fcsandbox20260509.client import Client as FCSandboxClient
from alibabacloud_tea_openapi import models as open_api_models
from e2b import Sandbox

REGION = "cn-hangzhou"
TEAM_ID = "<your-team-id>"  # See the prerequisites in "Build and Manage Templates via OpenAPI".

config = open_api_models.Config(
    access_key_id=os.environ["ALIBABA_CLOUD_ACCESS_KEY_ID"],
    access_key_secret=os.environ["ALIBABA_CLOUD_ACCESS_KEY_SECRET"],
    region_id=REGION,
    endpoint=f"fcsandbox.{REGION}.aliyuncs.com",
)
pop_client = FCSandboxClient(config)

# 1. Create a second-generation template and submit the build, baking the HTTP
#    service into the template.
resp = pop_client.create_template(
    models.CreateTemplateRequest(
        body=models.CreateTemplateInput(
            name=f"my-service-{int(time.time())}",
            team_id=TEAM_ID,
            runtime_config=models.CreateTemplateRuntimeConfig(
                cpu=2,
                memory_size=2048,
                disk_size=15360,
                sandbox_config=models.CreateTemplateSandboxConfig(
                    image=f"fc-e2b-registry.{REGION}.cr.aliyuncs.com/runtime/base:v0.0.52",
                    # Start and ready commands are supported only on the second-generation runtime.
                    generation=2,
                    # The start command runs as a background process during the build.
                    start_command="python3 -m http.server 8000",
                    # The ready command runs repeatedly until it exits with code 0.
                    ready_command="curl -sf http://localhost:8000/ > /dev/null",
                ),
            ),
        )
    )
)
template_id = resp.body.template_id

# 2. Poll the build status until the template is ready.
deadline = time.time() + 900
while True:
    got = pop_client.get_template(template_id, models.GetTemplateRequest(team_id=TEAM_ID))
    state = got.body.status.state
    if state == "ready":
        break
    if state == "error":
        raise SystemExit(f"Build failed: {got.body.status.reason.message}")
    if time.time() > deadline:
        raise SystemExit("Build timed out")
    time.sleep(10)

# 3. The template snapshot already contains the running service, so the sandbox
#    is accessible immediately after creation.
sandbox = Sandbox.create(
    template=template_id,
    timeout=600,
    # The SDK reads E2B_API_KEY / E2B_API_URL / E2B_DOMAIN from the environment;
    # you can also pass api_url and domain explicitly per region.
    api_url=f"https://api.{REGION}.e2b.fc.aliyuncs.com",
    domain=f"{REGION}.e2b.fc.aliyuncs.com",
)
try:
    host = sandbox.get_host(8000)
    print(f"https://{host}")
finally:
    sandbox.kill()
```

Delete templates that are no longer needed: `pop_client.delete_template(template_id, models.DeleteTemplateRequest(team_id=TEAM_ID))`.

## Run background commands in a sandbox

For long-lived processes that do not need to be baked into a template, start them with a background command after creating the sandbox.

Python example:

```python
server = sandbox.commands.run(
    "python3 -m http.server 8000",
    background=True,
)

host = sandbox.get_host(8000)
print(f"https://{host}")
```

TypeScript example:

```typescript
const server = await sandbox.commands.run("python3 -m http.server 8000", {
  background: true,
});

const host = sandbox.getHost(8000);
console.log(`https://${host}`);
```
