# Configure RAM User Permissions

Enterprises typically use one Alibaba Cloud account to own cloud resources and use RAM users, RAM user groups, or RAM roles to delegate management permissions. This topic explains how to limit FC Agent Sandbox permissions to specified resource groups, Teams, or resource types based on common scenarios.

## Choose the credential for your use case

| Access method | Credential | FCSandbox RAM permissions required |
| --- | --- | --- |
| Manage Teams, API Keys, and other resources in the console | Alibaba Cloud account or RAM user | Yes |
| Call FCSandbox OpenAPI | Alibaba Cloud AK or STS temporary credentials | Yes |
| Create and access sandboxes through the E2B SDK, E2B CLI, or compatible HTTP APIs | FC Agent Sandbox API Key | No |

Each FC Agent Sandbox API Key is bound to one Team. RAM policies control access to the console and OpenAPI, but do not further restrict an issued API Key. Therefore, a business application that only uses the E2B SDK generally does not need FCSandbox RAM permissions.

This topic does not cover the function execution RAM role that a Sandbox uses to access services such as OSS or AgenticFS. For those configurations, see [Mount OSS with Volumes](../04.Features/07.FC%20Extensions/07.Mounting%20OSS%20with%20Volumes.md) and [Mount AgenticFS with Volumes](../04.Features/07.FC%20Extensions/08.Mounting%20AgenticFS%20with%20Volumes.md).

## Plan resources and user permissions

When multiple teams share one Alibaba Cloud account, divide resource groups by business team and environment, and create a Team for each project. For example:

```text
Alibaba Cloud account
├── Resource group: Team A test
│   ├── Team: Data analytics test
│   └── Team: Machine learning test
├── Resource group: Team A production
│   ├── Team: Data analytics production
│   └── Team: Machine learning production
├── Resource group: Team B test
└── Resource group: Team B production
```

Recommended permission scopes:

| Identity | Recommended permission scope |
| --- | --- |
| FC Agent Sandbox platform administrator | All FC Agent Sandbox resources in the account |
| Business team administrator | Test and production resource groups of the business team |
| Project developer | A specified test Team |
| Production operator | A specified production Team |
| Automation program | Only the required resource types in a specified Team |
| Business application | Only the FC Agent Sandbox API Key of the corresponding Team |

Use resource groups as permission boundaries for teams and environments, and use Teams as project boundaries. Place test and production environments in separate resource groups so that test permissions do not allow developers to modify production resources. For Team resource relationships, see [Create a Team](02.Create%20a%20Team.md).

## Configure RAM permissions

1. Log on to the [RAM console](https://ram.console.aliyun.com/) by using an Alibaba Cloud account or a RAM user that has RAM administration permissions.
2. Create a custom policy and select **JSON Editor**. For instructions, see [Create a custom policy](https://www.alibabacloud.com/help/en/ram/user-guide/create-a-custom-policy).
3. Replace the region, account ID, resource group IDs, and Team IDs in the policy for your scenario.
4. Attach the policy to the target RAM user, RAM user group, or RAM role. For RAM users, see [Grant permissions to a RAM user](https://www.alibabacloud.com/help/en/ram/user-guide/grant-permissions-to-the-ram-user).
5. Use the target RAM identity to verify that required operations succeed and operations outside the authorized scope are denied.

### Scenario 1: Manage all FC Agent Sandbox resources in an account

This scenario applies to a platform administrator who manages all Teams and resources. The following policy grants only FCSandbox permissions in the specified account and region. It does not grant permissions on Function Compute or other Alibaba Cloud services.

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "fcsandbox:*",
      "Resource": "acs:fcsandbox:<region>:<account-id>:*"
    }
  ]
}
```

### Scenario 2: Manage resource groups of a business team

This scenario applies to an administrator who manages the test and production environments of one business team but cannot access other teams. The following example limits permissions to two resource groups:

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "fcsandbox:*",
      "Resource": "acs:fcsandbox:<region>:<account-id>:*",
      "Condition": {
        "StringEquals": {
          "acs:ResourceGroupId": [
            "<test-resource-group-id>",
            "<production-resource-group-id>"
          ]
        }
      }
    }
  ]
}
```

After logging on to the console, the RAM user must switch to an authorized resource group. When calling list operations, also specify the corresponding `resourceGroupID`.

### Scenario 3: Manage only a specified Team

This scenario applies to project developers or production operators. The following policy allows management of the specified Team and its child resources, but does not allow the identity to create other Teams:

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "fcsandbox:*",
      "Resource": [
        "acs:fcsandbox:<region>:<account-id>:teams/<team-id>",
        "acs:fcsandbox:<region>:<account-id>:teams/<team-id>/*"
      ]
    }
  ]
}
```

The Team and its child resources use separate ARNs, so both Resource entries are required. This policy does not include account-level Team list permissions. If the user must select a Team in the console, add `fcsandbox:ListTeams` permission scoped to the resource group. The user can then see the Team list in the same resource group. To strictly limit Team visibility, use a separate resource group for the project.

### Scenario 4: Allow automation to manage Volumes in one Team

This scenario applies to an automation program that only creates, queries, and deletes Volumes. Use a RAM role and STS temporary credentials:

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "fcsandbox:CreateVolume",
        "fcsandbox:ListVolumes",
        "fcsandbox:GetVolume",
        "fcsandbox:UpdateVolume",
        "fcsandbox:DeleteVolume"
      ],
      "Resource": "acs:fcsandbox:<region>:<account-id>:teams/<team-id>/volumes/*"
    }
  ]
}
```

Specify the corresponding Team ID when calling Volume operations. If the Team ID is omitted, list operations are authorized against the account-level Volume collection, which does not match this Team-level policy.

### Scenario 5: Allow a business application to create and access sandboxes

An administrator creates a dedicated Team and API Key for the application. The application uses the API Key with the E2B SDK and does not need an Alibaba Cloud AK or FCSandbox RAM permissions.

Use separate Teams and API Keys for different projects and environments. Do not share an API Key between test and production applications. For instructions, see [Create an API Key](03.Create%20an%20API%20Key.md).

## Verify the authorization results

After configuration, verify both allowed and denied operations:

| Identity | Expected to be allowed | Expected to be denied |
| --- | --- | --- |
| Platform administrator | Manage all Teams and resources in the account | Resources of other accounts |
| Business team administrator | Manage Teams and resources in authorized resource groups | Resource groups of other business teams |
| Project developer | Manage the specified test Team | Other projects and production Teams |
| Production operator | Manage the specified production Team | Test Teams and other production Teams |
| Volume automation program | Manage Volumes in the specified Team | API Keys, Volumes in other Teams, and other unauthorized resources |
| Business application | Create and access sandboxes by using an API Key | Manage Teams, API Keys, or Volumes through OpenAPI |

## Common mistakes

- **Sharing one Team across all projects**: Project members cannot effectively isolate API Keys, Templates, sandboxes, and Volumes. Use a separate Team for each project and environment.
- **Sharing a resource group between test and production**: Resource group authorization may give developers access to production resources. Use separate resource groups for test and production.
- **Using AdministratorAccess for convenience**: This policy grants permissions beyond FC Agent Sandbox. Use an `fcsandbox` custom policy when the identity only manages FC Agent Sandbox.
- **Confusing RAM permissions with FC Agent Sandbox API Keys**: RAM permissions control the console and OpenAPI. API Keys are used by the E2B SDK, CLI, and compatible HTTP APIs.
- **Authorizing only a Team or only its child resources**: `teams/<team-id>` does not include `teams/<team-id>/*`. Configure both when managing the whole Team.
- **Ignoring list permission scope**: List operations may use collection ARNs. Before granting collection permissions, confirm that the user is allowed to see all resources in that scope.

## Appendix: Resource ARN rules

### Basic ARN format

```text
acs:fcsandbox:<region>:<account-id>:<resource-path>
```

| Placeholder | Description |
| --- | --- |
| `<region>` | Region of the FC Agent Sandbox resource, such as `cn-beijing` |
| `<account-id>` | ID of the Alibaba Cloud account that owns the resource |
| `<team-id>` | Team ID |
| `<template-id>` | Template ID |
| `<volume-id>` | Volume ID |

### Common matching rules

| Resource expression | Matching scope |
| --- | --- |
| `acs:fcsandbox:<region>:<account-id>:*` | All FC Agent Sandbox resources in the specified account and region |
| `acs:fcsandbox:*:<account-id>:*` | FC Agent Sandbox resources of the specified account in all regions |
| `acs:fcsandbox:<region>:<account-id>:teams/*` | Teams in the account, excluding Team child resources |
| `acs:fcsandbox:<region>:<account-id>:teams/<team-id>` | A specified Team, excluding its child resources |
| `acs:fcsandbox:<region>:<account-id>:teams/<team-id>/*` | All child resources of a specified Team, excluding the Team itself |
| `acs:fcsandbox:<region>:<account-id>:teams/*/templates/*` | Templates in all Teams and sandboxes authorized against those Template ARNs |
| `acs:fcsandbox:<region>:<account-id>:teams/<team-id>/templates/*` | Templates in a specified Team and sandboxes authorized against those Template ARNs |
| `acs:fcsandbox:<region>:<account-id>:teams/<team-id>/templates/<template-id>` | A specified Template and sandboxes authorized against that Template ARN |
| `acs:fcsandbox:<region>:<account-id>:teams/*/apikeys/*` | API Keys in all Teams |
| `acs:fcsandbox:<region>:<account-id>:teams/<team-id>/apikeys/*` | API Keys in a specified Team |
| `acs:fcsandbox:<region>:<account-id>:teams/*/volumes/*` | Volumes in all Teams |
| `acs:fcsandbox:<region>:<account-id>:teams/<team-id>/volumes/*` | All Volumes in a specified Team |
| `acs:fcsandbox:<region>:<account-id>:teams/<team-id>/volumes/<volume-id>` | A specified Volume |
| `acs:fcsandbox:<region>:<account-id>:teams/*/quotas/*` | Quotas of all Teams |
| `acs:fcsandbox:<region>:<account-id>:teams/<team-id>/quotas/*` | Quotas of a specified Team |

A Sandbox does not have an independent Resource ARN. Sandbox operations are authorized against the ARN of the associated Template. Resource determines the scope of accessible Templates and associated sandboxes, while Action determines which Template or Sandbox operations are allowed.

API Keys and quotas support only Team-level authorization and cannot be limited to a single API Key or quota record. Depending on the request scope, list operations may use an account-level or Team-level collection ARN. If an identity has only Team-level permissions, explicitly specify the Team ID when calling a list operation that supports it.
