# Template Management

This page explains how to delete, get, and list templates, and how to troubleshoot template build issues. The examples use a template ID.

## Prerequisites

Configure the FC Agent Sandbox API key, API URL, and domain. Replace `<region>` with the region that contains the template.

```bash
export E2B_API_KEY="<your-api-key>"
export E2B_API_URL="https://api.<region>.e2b.fc.aliyuncs.com"
export E2B_DOMAIN="<region>.e2b.fc.aliyuncs.com"
export TEMPLATE_ID="<template-id>"
```

The Python examples use the `requests` library:

```bash
pip install requests
```

## Delete a template

Deletion cannot be undone. Confirm the template ID before deleting a template that may still be in use.

### curl

```bash
curl --request DELETE \
  --url "${E2B_API_URL}/templates/${TEMPLATE_ID}" \
  --header "X-API-Key: ${E2B_API_KEY}"
```

### Python requests

```python
import os

import requests

api_url = os.environ["E2B_API_URL"].rstrip("/")
template_id = os.environ["TEMPLATE_ID"]

response = requests.delete(
    f"{api_url}/templates/{template_id}",
    headers={"X-API-Key": os.environ["E2B_API_KEY"]},
    timeout=30,
)
response.raise_for_status()
print(f"Deleted template: {template_id}")
```

### E2B CLI

The following command asks for confirmation before deleting the template:

```bash
e2b template delete "${TEMPLATE_ID}"
```

In an automation script, add `--yes` to skip confirmation only after the script validates `TEMPLATE_ID`.

## Get a template

The get endpoint returns template details and build records for a template ID.

### curl

```bash
curl --request GET \
  --url "${E2B_API_URL}/templates/${TEMPLATE_ID}" \
  --header "X-API-Key: ${E2B_API_KEY}"
```

### Python requests

```python
import json
import os

import requests

api_url = os.environ["E2B_API_URL"].rstrip("/")
template_id = os.environ["TEMPLATE_ID"]

response = requests.get(
    f"{api_url}/templates/{template_id}",
    headers={"X-API-Key": os.environ["E2B_API_KEY"]},
    timeout=30,
)
response.raise_for_status()
print(json.dumps(response.json(), ensure_ascii=False, indent=2))
```

### E2B CLI

E2B CLI does not currently provide a separate `template get` command. Output the template list as JSON, then use `jq` to select the template ID:

```bash
e2b template list --format json \
  | jq --arg template_id "${TEMPLATE_ID}" \
      '.[] | select(.templateID == $template_id)'
```

This command returns the list summary for the template. To retrieve template details and build records, use curl or Python requests.

## List templates

The list endpoint returns templates visible to the current account in the target region.

### curl

```bash
curl --request GET \
  --url "${E2B_API_URL}/templates" \
  --header "X-API-Key: ${E2B_API_KEY}"
```

### Python requests

```python
import json
import os

import requests

api_url = os.environ["E2B_API_URL"].rstrip("/")

response = requests.get(
    f"{api_url}/templates",
    headers={"X-API-Key": os.environ["E2B_API_KEY"]},
    timeout=30,
)
response.raise_for_status()
print(json.dumps(response.json(), ensure_ascii=False, indent=2))
```

### E2B CLI

List templates in a table:

```bash
e2b template list
```

For machine-readable output, use JSON:

```bash
e2b template list --format json
```

## Template builds

### The E2B Template does not support passing steps or a Dockerfile inline; how do I build dependencies?

The Template Build API currently does not support passing `steps` (installation steps) or a Dockerfile inline in an E2B Template definition. Passing `steps` returns `400 steps are not supported`, so do not try to install dependencies online through build steps.

Only this usage—passing `steps` or a Dockerfile inline through the E2B Template definition—is unsupported; the Dockerfile itself still works. You can still build a finished image with a Dockerfile externally, and then build the template from your image registry with `from_image`.

Therefore, dependencies should be installed during the Dockerfile or external image build phase, and then the finished image should be pushed to an image registry so the template only builds from that image. This avoids downloading and installing dependencies during the template build or after every Sandbox creation.

Minimal Dockerfile example:

```dockerfile
FROM python:3.12-slim

# Install Python dependencies
RUN pip install --no-cache-dir pandas numpy

# Install system dependencies and clean the apt index
RUN apt-get update \
    && apt-get install -y --no-install-recommends git \
    && rm -rf /var/lib/apt/lists/*
```

Start with the error summary. If it is not sufficient to locate the failure, inspect the full build log for the failing phase, the `RequestId`, the image address, and the build configuration.

For the full custom image and template build flow, see [Build Custom Image Templates](../04.Features/02.Templates/03.Build%20Custom%20Image%20Templates.md).

### How do I troubleshoot private image pull or build failures?

Identify the failing phase in the full build log, then use the following table for common source image pull and image format issues.

| Failing phase | Typical error | Action |
| --- | --- | --- |
| Pulling the source image | `unauthorized`, `denied`, `manifest unknown`, or `not found` | Verify that the image address, tag, or digest exists. For ACR EE, confirm that the instance and FC Agent Sandbox use the same UID and region, that a VPC reachable by the build path is bound, and that the username, password, or token is valid. |
| Conversion or build | `invalid image, platform of image is unknown/unknown`, or manifest/provenance errors | Inspect the image manifest. Build a single `linux/amd64` platform image, disable provenance and SBOM, push a new tag, and retry. Do not reuse an old tag whose content may have changed. |

For the full custom image template build flow, see [Build Custom Image Templates](../04.Features/02.Templates/03.Build%20Custom%20Image%20Templates.md); for an end-to-end example of pulling from a private registry, see [Build a Sandbox Template from a GHCR Custom Image](../05.Best%20Practices/07.Build%20a%20Sandbox%20Template%20from%20a%20GHCR%20Custom%20Image.md).

### Why does the same image work in the first generation but not in the second? {#first-gen-works-second-gen-fails}

The following applies to `os_type=linux-amd64`. When the same image runs correctly in a first-generation template but fails to build or start in the second generation, the image is usually not defective. The two runtimes use different process models:

- **Entrypoint**: the first generation executes the image `ENTRYPOINT`/`CMD` with container semantics. The second generation is a micro VM whose PID 1 is systemd, and the image `ENTRYPOINT`/`CMD` is not executed. If the service was started by the entrypoint script, put the script or the command in `start_command`; there is no need to rewrite it as a systemd unit. Conversely, systemd services that are already enabled in the image start automatically, so do not start a second copy from the start command or the two processes will compete for the same port.
- **Environment variables**: in the first generation, the image `ENV` reaches every process in the container. In the second generation, the image `ENV` reaches only envd and the command processes it spawns (`commands.run`, the start command, the ready command) and does not enter systemd. A service started by systemd cannot read the variables, so any default port or path in the code silently takes effect; the ready command then keeps failing and the build times out after 5 minutes.
- **Base image**: the second generation requires an Ubuntu/Debian-based image that keeps system components such as `systemd`, `openssh-server`, `sudo`, `chrony`, `fuse3`, and `iptables` (or guarantees that `apt-get` works). Minimal rootfs images such as Alpine and BusyBox are not supported.
- **Execution identity**: the second-generation start and ready commands run as the template default user `user` (UID 1000 when available, otherwise the next free ID). They do not run as root and do not follow the image `USER`. Paths that require root or file handles such as `/dev/stdout` fail; use `sudo` (the image must provide sudo and a passwordless sudoers entry) or fix the file ownership in advance.
- **Snapshot side effects**: files written to `/tmp` or `$HOME` during the build, and state changes such as `systemctl disable`, are captured in the template snapshot and ship with every sandbox.

Troubleshooting order:

1. A successful local `docker run` only proves that the image itself works; it does not prove that a second-generation template will build. First check whether the service depends on the image entrypoint.
2. In a running sandbox, run `id`, `ps -ef`, and `sudo systemctl --no-pager status` to confirm which process starts the service and which identity it uses. Running `systemctl` as a non-root user fails with `Failed to connect to system scope bus`; that is expected and does not indicate a broken sandbox.
3. If systemd starts the service and the service depends on the image `ENV`, add a systemd drop-in with `EnvironmentFile=` in the image, or run `sudo -E systemctl import-environment <VAR1> <VAR2>` in `start_command` (importing the variables by name) and restart the service.
4. If the entrypoint script used to start the service, disable the conflicting systemd service in `start_command` and start the script explicitly, for example `sudo -E bash -c 'systemctl disable --now <service>; exec bash /start.sh' > /tmp/start.log 2>&1`.
5. Readiness depends only on the exit code and stdout is not returned; the stderr of the last failed attempt is included in the build failure reason, so you can print diagnostics from the ready command with `exec 1>&2`. Also make sure the probe address and port match the address and port the service actually listens on.

When a build fails, the console and API return the failed build step and the exit code. A failing start command does not fail the build by itself, so "the service never started" usually surfaces as a readiness timeout. For a fuller picture, redirect logs from `start_command` to a path writable by the default user, for example `> $HOME/start.log 2>&1`, and note that these files are captured in the template snapshot.
